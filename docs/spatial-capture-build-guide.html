00Reframe

One Space, not three screens

The instinct is to build a balcony editor, a garden editor, and a land editor. Resist it — you'd write the hard parts (sun, gridding, recommendations) three times and still have to special-case the “garden that's part raised-bed, part open ground” mix. Model everything as a single Space, and let the chosen type decide only how the boundary is seeded and which controls you show.

TypeBoundary seedHeadline inputEditor
balconyrectangle, drag cornerstap each edge: full / half / no wall + height, mark the door, toggle “slab above”constrained canvas
gardenfreeform polygonhouse wall & fences, trees, raised bedscanvas or map
landpolygon on satellitetrace the usable area, drop obstaclesmap (lat / long)

The “weird circular balcony” disappears the moment the boundary is a polygon rather than a fixed four-sided struct: the default UX still seeds a rectangle and the user taps four edges, but a power user can add vertices to trace an L-shape or approximate a curve. You never build a “curved balcony mode” — you just don't cap the rectangle at four sides.

The mixed-space answer A walled raised bed inside an open garden is a child Space with its own substrate (ground / raised-bed / container), nested in the parent and inheriting its light from where it sits. Composition, not a fourth type.

01Model

The data model & one coordinate frame

Pin the model first; everything downstream reads it. The single most important decision is the coordinate frame: store all geometry in local metres, with a separate georeference. Canvas-drawn balconies are already local metres; a map-drawn plot gets projected from lat/long into the same frame the instant it's captured. Doing grid and shadow maths in degrees of latitude is misery — convert once at the edges and the engine only ever sees metres.

src/spatial/types.ts 
// Everything is in local metres. +x = east, +y = north (before rotation).
type Vec2 = { x: number; y: number }

interface Edge {            // one segment of the boundary
  wall: 'full' | 'half' | 'none'
  height: number          // metres; 0 for 'none'
  door?: number            // 0..1 position of an opening along the edge
}

interface Obstacle {        // casts shade: pillar, neighbour wall, tree, shed
  footprint: Vec2[]
  height: number
}

interface Overhead {        // roof / the balcony slab above / pergola
  footprint: Vec2[]
  height: number          // clearance from the floor — blocks high midday sun
}

interface Space {
  type: 'balcony' | 'garden' | 'land'
  boundary: Vec2[]         // ordered polygon vertices
  edges: Edge[]            // edges[i] is boundary[i] → boundary[i+1]
  obstacles: Obstacle[]
  overhead?: Overhead
  geo: { lat: number; lng?: number; bearing: number } // bearing = rotation to true north
  zones?: Space[]          // raised beds / containers, nested
  substrate?: 'ground' | 'raised-bed' | 'container'
}

geo.lat is the only field the sun engine truly needs (latitude sets the sun's path); lng is optional and only used to pull climate data and to anchor the map trace. bearing rotates the local frame so “+y” lines up with true north.

02Boundary

Capture the boundary (three ways, one output)

Each input mode is just a different way to fill boundary: Vec2[]. Build them as three small components that all emit the same array.

Balcony — seeded rectangle

Render an SVG or canvas rectangle (default 3 × 2 m), with draggable corner handles snapping to 0.1 m. Keep it stored as a polygon. Add a “＋ add corner” affordance on any edge for the irregular cases. Acceptance: dragging a corner updates the live area readout and the four edges stay paired to their vertices.

Garden — freeform polygon

Tap to drop vertices, drag to adjust, close the loop. Same component as land but on a blank metric canvas instead of a map tile.

Land — trace on the map, then project

Drop a pin (this gives you lat/lng for free), draw the polygon on satellite imagery, then convert each ring point to local metres with a local equirectangular projection anchored at the boundary's first point:

src/spatial/project.ts 
const R = 6_378_137 // earth radius, metres

function toLocalMetres(p: LatLng, origin: LatLng): Vec2 {
  const rad = Math.PI / 180
  return {
    x: (p.lng - origin.lng) * rad * R * Math.cos(origin.lat * rad),
    y: (p.lat - origin.lat) * rad * R,
  }
}

For a plot a few hundred metres across, the flat-earth error is centimetres — fine. From here on, land is identical to a garden: same polygon, same grid, same engine.

03Structure

Walls, doors, obstacles, and which way is north

This is where the balcony editor earns its keep, because on a small space the walls are the whole story for sun. For each edge, let the user cycle full → half → none and set a height; drop a door marker; and — critically — toggle an overhead (“is there a floor/roof above you?”) with a clearance height. The slab above is usually the biggest occluder on a balcony and the easiest thing to forget.

  • Obstacles: tap to place a footprint + height — the building you're attached to, a neighbour's wall, a mature tree, a shed.
  • Orientation: a compass dial setting geo.bearing. On mobile you can seed it from the device magnetometer (“point your phone at the open side”), then let them nudge it.
  • Latitude: geocode the city you already collect in onboarding step 1, or read GPS. No new question needed.
Other inputs worth collecting for garden & land A water access point (drag a tap/hose origin → feeds a tending-effort score), wind exposure (open edges, brutal on high balconies), the house wall (shade caster and reflected heat — a warm microclimate), and on land, slope & aspect pulled from an elevation API. Latitude also hands you the climate/hardiness zone, which gates the whole plant catalog.
04Sun engine

Compute the light — don't ask for it

The current Insolação dropdown asks the user to run the simulation in their head, badly. You already have the inputs to compute it. Do it in two tiers and ship the cheap one first.

Tier 1 — orientation × latitude (ship this in v1)

The bearing of the open side plus latitude already gives a solid coarse class. In the southern hemisphere a north-facing balcony bakes; a south-facing one stays shady. This single calculation can replace the manual dropdown with a derived value and a confidence note — no geometry needed.

Tier 2 — the 2.5-D shadow model (the real payoff)

For each hour of a few representative days, get the sun's position, project every wall, obstacle, and the overhead into a shadow polygon on the ground, and accumulate “sun-hours” per grid cell. “2.5-D” means you never build a 3-D mesh — just 2-D footprints carrying a height.

Step 1 — sun position. Use a library rather than reinventing it; SunCalc's getPosition(date, lat, lng) returns altitude and azimuth. The underlying geometry, so you understand what it returns:

solar geometry — the core of what SunCalc does 
// δ declination, H hour angle, φ latitude — all radians
const alt = Math.asin( sin(φ)*sin(δ) + cos(φ)*cos(δ)*cos(H) )
const az  = Math.atan2( sin(H), cos(H)*sin(φ) - tan(δ)*cos(φ) )
// alt <= 0  → sun is down, skip this hour entirely

Step 2 — project a shadow. A vertical occluder of height h at sun altitude α casts a shadow of length L = h / tan(α) in the anti-sun direction. The shadow polygon is the convex hull of the footprint and the footprint translated by that vector. A floating overhead slab is the same translation, minus the hull (the shadow is just the displaced footprint).

src/spatial/shadow.ts 
function shadowOffset(altRad: number, azRad: number, h: number): Vec2 {
  const len = h / Math.tan(altRad)        // long at dawn/dusk, short at noon
  return {                                  // points away from the sun
    x: -len * Math.sin(azRad),
    y: -len * Math.cos(azRad),
  }
}

function wallShadow(foot: Vec2[], off: Vec2): Vec2[] {
  const moved = foot.map(p => ({ x: p.x + off.x, y: p.y + off.y }))
  return convexHull([...foot, ...moved])  // vertical occluder
}

Step 3 — integrate over the year. Loop three representative days (summer solstice, equinox, winter solstice — enough to capture the seasonal swing) × daylight hours. Each hour, union all shadow polygons and add the hour to every cell that's not covered. Store summer and winter sun-hours separately — a south wall that's sunny in December is the whole game for cool-season crops.

src/spatial/sunGrid.ts — the integration loop 
for (const day of [SUMMER, EQUINOX, WINTER]) {
  for (let hour = 5; hour <= 20; hour += 0.5) {
    const { altitude, azimuth } = getSunPosition(day, hour, space.geo)
    if (altitude <= 0) continue                  // night
    const shadows = [
      ...occluders(space).map(o => wallShadow(o.foot, shadowOffset(altitude, azimuth, o.h))),
      ...overheadShadows(space, altitude, azimuth),
    ]
    rasterizeShadows(grid, shadows)               // draws straight onto the cell array
    for (const cell of grid.litCells()) cell.sunHours[day.season] += 0.5
  }
}
Performance Don't run point-in-polygon for every cell × every shadow × every hour. Rasterize the shadow polygons straight onto the grid (scanline-fill them into the cell array, like drawing filled polygons) and read “lit vs shaded” back per cell. A balcony is ~100 cells and the whole year-loop runs in a few milliseconds.

Let the user correct it

Finish with a paint-over layer: “this corner is always shady.” It captures the neighbour's tree you didn't trace without forcing the user to model anything. The photo you already collect in onboarding step 4 can later auto-seed obstacles.

05Grid

Rasterize the space into scored cells

Lay a grid over the boundary's bounding box — 0.25 m cells for a balcony, 0.5 m for a garden, 1 m+ for land (downsample big plots). Keep a cell only if its centre passes a point-in-polygon test against the boundary and isn't under a fixed obstacle. Each surviving cell carries the feature vector the recommender reads:

src/spatial/types.ts — the cell 
interface Cell {
  pos: Vec2
  sunHours: { summer: number; winter: number }
  light: 'full' | 'partial' | 'shade'  // bucketed from sunHours
  nearWall: number     // 0..1 — warm microclimate / heat retention
  wind: number         // 0..1 — exposure from open edges
  access: number       // 0..1 — closeness to the door, ease of tending
  slope?: number; aspect?: number; soil?: string  // land only
}

The heatmap in the hero above is exactly this grid, coloured by sunHours. That visual is the deliverable — it's what makes PlantAI feel like it understands the space rather than like a longer form.

06Matcher

Fit plants to cells

Recommendation becomes a scoring-and-placement problem. Give each catalog plant its requirements, score it against every cell, then place greedily from the best matches while respecting spacing and shading rules.

src/spatial/match.ts 
interface PlantReq {
  minSun: number; maxSun: number  // summer sun-hours the plant wants
  spacing: number               // metres between plants
  height: number; water: 'low' | 'med' | 'high'
}

function score(plant: PlantReq, c: Cell): number {
  const s = c.sunHours.summer
  if (s < plant.minSun || s > plant.maxSun) return 0  // hard miss
  return fit(s, plant) * c.access * water(plant, c)   // soft preferences
}

Two placement rules turn a scatter of plants into a real plan:

  • Spacing: once a plant is placed, block other cells within its spacing radius.
  • Height / shading: never place a tall plant on the sun side of a shorter light-lover, or it shades it out. The sun side is just the average azimuth from the grid you already computed.

The output maps cleanly onto the app's existing GardenZone and PlantRecommendation types — the matcher's clusters become the semantic zones (horta, frutas, aromas) painted on top of the suitability grid. Note the distinction: the grid is the physical substrate; zones are the meaning laid over it.

08React

The visualizer, in plain React

The companion studio (docs/sun-map-studio.html) is one <canvas> and plain JavaScript. Moving it into React needs almost no React-specific cleverness — the whole trick is knowing what belongs in React and what must stay out of it. You want exactly the toggle you described: animate the engine, or just show the sun-hours map.

Split the engine from the view

Keep all the maths in a framework-free engine.ts — pure functions that take data and return data. No React, no canvas, no DOM. That's what let me run the whole simulation in Node to sanity-check the numbers before ever opening a browser; you get the same free testability.

engine.ts — pure, testable, no React 
export function sun(t: number): Sun { /* angle of the sun at time t */ }
export function shadowOf(occ: Occluder, s: Sun): Vec2[] { /* projected polygon */ }
export function pip(x: number, y: number, poly: Vec2[]): boolean { /* in shadow? */ }
export function buildGrid(scene: Scene): Grid { /* integrate sun-hours over the day */ }

The golden rule: never drive the loop through state

A 60 fps animation that calls setState every frame re-renders your component tree 60 times a second — guaranteed jank. So React state holds only what a human changes (which scene, which mode, the opacity, playing or paused). The per-frame drawing happens imperatively, straight onto a canvas you reach through a ref. This little hook is the entire animation machinery:

useAnimationFrame.ts 
function useAnimationFrame(onFrame: (dt: number) => void, active: boolean) {
  const cb = useRef(onFrame); cb.current = onFrame;   // always the latest closure — no stale t
  useEffect(() => {
    if (!active) return;                            // paused / static mode → no loop at all
    let raf: number, last: number | null = null;
    const loop = (ts: number) => {
      if (last == null) last = ts;
      const dt = (ts - last) / 1000; last = ts;        // seconds since previous frame
      cb.current(dt);
      raf = requestAnimationFrame(loop);
    };
    raf = requestAnimationFrame(loop);
    return () => cancelAnimationFrame(raf);          // cleanup — without this StrictMode runs TWO loops
  }, [active]);
}

Two details earn their keep. The cb ref means the loop always calls the freshest version of your draw function, so it sees the current t without you restarting the loop on every render. And the cleanup cancelAnimationFrame is not optional — React 18's StrictMode mounts effects twice in development, and without cleanup you get two loops racing, which looks like the sun moving at double speed.

The animate ↔ static toggle (your idea)

One boolean drives everything. In animate mode the hook is active, advances time, and redraws live shadows. In static mode the hook is inert (literally no loop running) and a plain effect paints the sun-hours map once whenever the scene or opacity changes.

SceneCanvas.tsx 
function SceneCanvas({ scene, mode, opacity }: Props) {
  const ref = useRef<HTMLCanvasElement>(null);
  const tRef = useRef(0.34);                          // time-of-day lives in a ref, not state
  const grid = useMemo(() => buildGrid(scene), [scene]); // heavy integral — once per scene

  // STATIC: redraw the sun-hours map only when inputs change and we're not animating
  useEffect(() => {
    if (mode !== 'animate') drawSunHours(ref.current!, scene, grid, opacity);
  }, [scene, grid, opacity, mode]);

  // ANIMATE: the loop only exists while mode === 'animate'
  useAnimationFrame((dt) => {
    tRef.current = (tRef.current + dt / 12) % 1;        // 12 real seconds = one full day
    drawLive(ref.current!, scene, grid, tRef.current, opacity);
  }, mode === 'animate');

  return <canvas ref={ref} />;
}
Why useMemo on the grid buildGrid runs the whole-day shadow integral — the expensive part. It depends only on the scene, not on time or opacity, so useMemo([scene]) means switching opacity or scrubbing time never recomputes it. The sun-hours map is computed once and reused by both modes.

The remaining glue

  • Crisp on retina: set canvas.width = cssWidth * devicePixelRatio and scale the context by the same factor; use a ResizeObserver to refit on layout changes.
  • Reduced motion: read matchMedia('(prefers-reduced-motion: reduce)') and default mode to static — the map still tells the whole story without movement.
  • The clock readout: keep t in the ref for drawing, but to show "12:30" on screen, setState only a few times per second (throttle it) — the eye can't read faster than that anyway, and you keep React out of the hot path.
Part II · build it for real
From the concept to a working editor & studio — vanilla.

Part I is the thinking and the appendix is the maths; this is the build. An Editor that authors a Space, a map-image workflow that needs no map library, and a Studio that analyzes the space over time with live controls and hand-drawn charts — nine sections, each a real step, no third-party tools. Every shared type and function has exactly one home; the rest import it.

B·0Architecture

Two apps, one engine

Part I shipped a single onboarding question. Part II ships a tool. The honest way to frame the rest of this build is that you are writing two front-ends over one back-end — except the "back-end" is a pure module that runs in the same tab. An Editor lets the user author a Space: trace a boundary, raise walls, drop obstacles, point north, optionally drop in a photo of the plot. A Studio takes that exact Space and renders it over a day — the orbiting sun, the moving cast shadows, the sun-hours heatmap, the plant matches. Neither app knows the other exists. They share exactly two things: a serializable Space (plain JSON, no class instances, no functions) and a pure engine module (sunAt, shadowOf, occludersOf, buildGridSeries, cellAt, cellHourly, microclimate — defined in Section B·6, with the transform helpers makeT/toWorld/Viewport in Section B·2).

That split is the single most important architectural decision in Part II, and it is worth being dogmatic about it. The engine is the asset. It is the thing you test, the thing you run inside a Web Worker, the thing a future native app could reuse. The Editor and Studio are disposable React — views that produce and consume a Space. If you ever feel an engine function reaching for useState, a ctx, or window, you have crossed the boundary and introduced a bug you will pay for later. This section is architecture only: it names the seams and shows how the pieces fit. The real bodies live in their home sections — do not copy them here, import them.

The boundary: one pure module, two React consumers

The engine exports only pure functions — same input, same output, no side effects, no DOM. The canvas, the React state, and the localStorage all live on the *outside*. This is what makes the engine testable in a *.test.ts with zero mocking, and what lets you later post a Space to a Worker and get a Grid back without rewriting a line (see Section B·8 for the worker wiring; the useAnimationFrame hook is from Phase 08). The three seams every other section depends on are:

  • Model + persistence (home: Section B·1). The Space/Edge/Obstacle/Overhead/BaseImage/Cell types and the one SpaceStore module that round-trips them through localStorage under KEY = "plantai.spaces.v1". There is no second persistence module — B·0, B·5, and B·8 all import SpaceStore, none reimplement it.
  • Coordinates + transform (home: Section B·2). makeT(space, CW, CH, padM) derives its bounds from space.boundary (no world field, no synthetic world object), toWorld(T, sx, sy) inverts it through the public T only, and Viewport composes makeT and layers pan/zoom on top — it does not redefine the transform.
  • The engine (home: Section B·6). Occluder, shadowOf, occludersOf, sunAt, SEASONS, the typed-array Grid, buildGridSeries, cellAt, cellHourly, microclimate, lightClass. The geometry primitives hull and pip are from Appendix A·4 — imported, never re-derived.
Keep the boundary honestThe engine must never import React and never touch document, window, localStorage, or a CanvasRenderingContext2D. makeT is the one borderline case — it returns *closures over numbers* (X, Y, S, scale, cx, cy), which is still pure: it computes a transform, it does not draw. The actual ctx.fill() calls live in the React canvas layer. Likewise, whether an occluder casts a vertical-hull shadow or a floating translate is a property of the data, not the caller: the canon Occluder carries kind: "vertical" | "overhead", and shadowOf branches on occ.kind. There is no overhead boolean argument. If a lint rule could enforce one thing in Part II, make it no-restricted-imports of react inside engine/.

Data-flow: Editor → Space JSON → SpaceStore → Studio → Grid

The whole product is one unidirectional pipe. The Editor's only job is to emit a valid Space. SpaceStore (Section B·1) is the thin localStorage seam — one blob, a map of id → Space, plus a schemaVersion that migrate bumps forward on read. The Studio reads a Space by id and turns it into a Grid via buildGridSeries; the Grid then feeds both the heatmap and the plant matcher (the matcher itself is Phase 06). Nothing flows backward — the Studio never mutates the Space; if the user wants to fix the geometry, they reopen the Editor.

The no-third-party stance, made concrete

The constraint is not asceticism for its own sake — the browser already ships the primitives this product needs, and every one of them is a stable, spec'd, zero-bundle API. Here is the exact mapping of "feature" to "platform primitive that gives it to you for free":

  • Drawing + hit-testing → Canvas 2D. fill/stroke/clip render the plan; ctx.isPointInPath(x,y) and the imported pip() (Appendix A·4) do hit-tests for picking a wall or a cell. No Konva, no Fabric, no Paper.
  • Map / photo import → FileReader + Image / createImageBitmap. The user drops a photo or screenshot; FileReader.readAsDataURL gives you the BaseImage.dataUrl, Image/createImageBitmap decodes it, and you drawImage it under the plan at the calibrated scale (Section B·5). Image-pixel → world metres is imagePxToWorld(pImg, calibration); a screen-px length → metres is Viewport.pxToMetres(lenPx) — different things, different names.
  • Persistence → localStorage. A Space is pure JSON, so JSON.stringify round-trips it with no ORM and no schema engine. SCHEMA_VERSION + migrate handle upgrades by hand. The single ~5MB-budget blob is SpaceStore's job (Section B·1); an optional large-image path stores a Blob in IndexedDB keyed by space id.
  • Off-thread compute → Web Worker. buildGridSeries over a big land plot at a fine cellSize can take tens of ms; post the Space to a worker (a structured-clone-friendly plain object — no transferables needed for the input) and the returned Grid of typed arrays comes back transferable so the main thread stays at 60fps (Section B·8).
  • Animation → requestAnimationFrame. The Studio's sun sweep is a delta-timed rAF loop driving ctx directly — never React state per frame (Appendix A·3, Phase 08).
The only two places a dependency tempts youThere are exactly two problems in this build where reaching for a library feels natural — and both have a vanilla answer. 1. Slippy map tiles (Leaflet/Mapbox/OpenLayers) for the land tracer. You do NOT need a live tile server. The user supplies a static image — a satellite screenshot or a sketch — which becomes BaseImage.dataUrl. Two tapped reference points (BaseImage.georef.a, BaseImage.georef.b with known lat/lng, or just a known on-image distance) calibrate metresPerPixel. That is the whole map. A draft that pulls in a tile lib is a defect. 2. Precise solar position (a solar/ephemeris lib). buildGridSeries already uses the real spherical sunAt (Cooper declination + hour angle, Appendix A·2) for ALL analysis. The simplified sun(t) arc from the prototype is kept ON PURPOSE for the live animation visual only. The only sanctioned external mention is SunCalc (~1KB), and even that stays an *optional aside* beside the Appendix A·2 formulas — never the default.
Two suns, on purpose — don't collapse themIt is easy to misread the engine as having a redundant solar model. It does not. sun(t) (t in [0,1] across daylight, the simplified southern-hemisphere arc lifted from docs/sun-map-studio.html) drives the live animation visual only — the orbiting disc and the smoothly sweeping shadows you watch. sunAt(dayOfYear, hour, latRad) is the real spherical position (declination, hour angle, altitude/azimuth) used for all analysis — every cell's sunHours and the hourly exposure series come from sunAt, never from sun(t). Keep both; do not introduce a third winter model — SEASONS already carries summer/equinox/winter day-of-year values.

B·1Data model

The Space, serialized

Everything you author in the editor has to survive a page reload, a localStorage round-trip, and being carried between two screens — the editor that writes it and the studio that reads it. That contract is one JSON object: a Space. If a value can be re-derived from the boundary, edges, obstacles, and geo, it does not belong in that object. The Space is the *input*; the Grid and its sun-hours are *output*. We persist inputs and recompute outputs, every time.

This section is the canonical home for three things the rest of Part II imports: the exact model types (introduced in Phase 01, written out in full here), a zero-dependency SpaceStore over localStorage, and JSON import/export. Sections B·0, B·5, and B·8 import this module — they never reimplement it. No ORM, no IndexedDB wrapper (one optional large-image path aside), no uuid package — just the platform, plus a schemaVersion + migrate() discipline so a Space written today still opens next month.

The persisted types

Vec2 is local metres, +x east, +y north — the same frame the engine (sunAt, shadowOf, occludersOf) and the transform (makeT, see Section B·2) assume. Note what is *absent*: there is no Grid, no Cell, no sunHours field anywhere in Space, and crucially no world field — makeT derives its bounds straight from space.boundary, so a Space never carries a precomputed world rect. Those omissions are deliberate and load-bearing (see the next section). The logical Cell type is listed here for reference only; the engine's actual Grid stores parallel typed arrays and materializes a Cell on demand via cellAt (defined in Section B·6).

Because a zone is itself a full Space, that same invariant holds for every nested zone, and migrate() repairs them recursively.

Why the Grid is never persisted

It is tempting to cache buildGridSeries(space) next to the Space — it can be expensive (a polygon rasterize plus a per-cell sun integration over three seasons, see Section B·6). Don't. The Grid, every cell's sunHours, and the light classification are pure functions of the Space plus the solar model. Three reasons to recompute rather than store:

  • Staleness is silent and dangerous. Move one obstacle in the editor and a persisted grid is instantly wrong, with no error to tell you. A derived value that can drift out of sync with its source is a bug waiting for a reload. Recomputing makes drift impossible.
  • The cost is wrong to pay at write time. buildGridSeries belongs to the studio, wrapped in useMemo keyed on the Space (see Phase 08), and ideally run in a worker (see Section B·8). The editor saves geometry in microseconds; the grid is computed once when the studio mounts and never written to disk.
  • The math evolves; the inputs don't. When the solar model improves (the simplified sun(t) arc for the live visual vs. the real sunAt for analysis, and optionally SunCalc — see Appendix A·2), a stored grid would be frozen at the old algorithm. Recomputing means every saved Space automatically benefits from a better engine with zero migration.
persist inputs, derive outputsThe litmus test for any field: *can I reconstruct this from boundary + edges + obstacles + overhead + geo?* If yes, it is output — leave it out of Space. sunHours, light, nearWall, wind, access, the whole Grid: all output, computed by the engine in Section B·6, never stored. There is also no world rect on Space — makeT recomputes the world bounds from boundary each render (Section B·2). The base image's dataUrl is input (you can't regenerate a photo), so it stays — but be aware it dominates payload size.

The SpaceStore over localStorage

localStorage is a synchronous string-to-string map. The store keeps one blob under a single versioned key, plantai.spaces.v1, shaped { [id]: Space }. Every read funnels each Space through migrate() so the rest of the app only ever sees a current-schema object; every write stamps schemaVersion = SCHEMA_VERSION. Ids come from crypto.randomUUID(). This is the *only* persistence module in Part II — B·0, B·5, and B·8 import SpaceStore; none of them re-open localStorage directly.

src/space/store.ts 
import { Space } from './types';

export const KEY = 'plantai.spaces.v1';
export const SCHEMA_VERSION = 1;

export const SpaceStore = {
  /** The raw id->Space map (current shape, NOT yet migrated). */
  all(): Record<string, Space> {
    try {
      return JSON.parse(localStorage.getItem(KEY) || '{}');
    } catch (e) {
      return {};
    }
  },

  /** Every space, migrated forward to the current schema. */
  list(): Space[] {
    return Object.values(this.all()).map(migrate);
  },

  /** Load one space, migrating it forward; null if absent. */
  load(id: string): Space | null {
    const s = this.all()[id];
    return s ? migrate(s) : null;
  },

  /**
   * Insert or update. Stamps the current schemaVersion, then rewrites the blob.
   * Throws QuotaExceededError synchronously if the payload exceeds the quota —
   * the caller must catch it (see the quota note).
   */
  save(space: Space): void {
    space.schemaVersion = SCHEMA_VERSION;
    const a = this.all();
    a[space.id] = space;
    localStorage.setItem(KEY, JSON.stringify(a));
  },

  remove(id: string): void {
    const a = this.all();
    delete a[id];
    localStorage.setItem(KEY, JSON.stringify(a));
  },

  /** Deep-clone a space under a fresh id; " copy" appended to the name. */
  duplicate(id: string): Space {
    const s = structuredClone(this.load(id)!);
    s.id = crypto.randomUUID();
    s.name = s.name + ' copy';
    this.save(s);
    return s;
  },

  /** One space as a downloadable JSON Blob (wire to URL.createObjectURL + a[download]). */
  export(id: string): Blob {
    return new Blob([JSON.stringify(this.load(id), null, 2)], {
      type: 'application/json',
    });
  },

  /** Read a user-picked File, migrate it, re-id it (never clobber), and persist. */
  import(file: File): Promise<Space> {
    return file.text().then(function (t) {
      const s = migrate(JSON.parse(t));
      s.id = crypto.randomUUID();
      SpaceStore.save(s);
      return s;
    });
  },
};

// migrate is the ONLY place that knows about old shapes; everything else codes
// against the current Space. See the migration section below for the full body.
export function migrate(raw: any): Space {
  // switch(raw.schemaVersion) to bump old shapes forward, then:
  raw.schemaVersion = SCHEMA_VERSION;
  return raw as Space;
}

/** A blank space of the given type — the editor's starting point. */
export function newSpace(type: Space['type']): Space {
  return {
    id: crypto.randomUUID(),
    name: 'Untitled',
    type: type,
    boundary: [],
    edges: [],
    obstacles: [],
    geo: { lat: -23.5, bearing: 0 }, // southern-hemisphere default
    schemaVersion: SCHEMA_VERSION,
  };
}

The blob holds *all* spaces at once, so a full-resolution base.dataUrl JPEG (1–3 MB each) blows the budget fast. Make the base image the default storage path but downscale it on a <canvas> to longest edge ≤ ~1600px and re-encode with canvas.toDataURL('image/jpeg', 0.8) before assigning base.dataUrl. Because save() lets the throw propagate, wrap the editor's save in try/catch and surface the quota error rather than letting an edit silently vanish. schemaVersion and forward-compatible migration

SCHEMA_VERSION is 1 today: this is the first persisted schema, so migrate() currently just stamps the version and returns. The reason we wire the discipline in *now*, before there is anything to migrate, is that the shape *will* change — and migration is the one place allowed to know about old shapes, so the rest of the app codes exclusively against the latest Space. The skeleton below shows how to grow it: a switch on raw.schemaVersion walks an older blob up one step at a time, then repairEdges restores the edges ↔ boundary invariant, and the walk recurses into zones (which are themselves Spaces).

One subtlety the canonical model forces on us: a zone is itself a full Space (zones?: Space[]), so an old blob's nested zones carry the *same* old shape as the root. migrate() must therefore recurse — migrate each zone the same way, and repair the edges ↔ boundary invariant on each zone too. Skip that and a future garden migrates fine while its raised-bed zone keeps a stale shape and a short edges array, which then breaks occludersOf/buildGridSeries for that sub-space (see Section B·6).

src/space/migrate.ts (skeleton for future versions) 
import { Space, Edge } from './types';
import { SCHEMA_VERSION } from './store';

// `any` is correct here: by definition we read shapes that predate the current
// types. migrate() is the boundary that launders unknown -> Space.
type AnySpace = Record<string, any>;

// One pure step per version bump. EMPTY today (SCHEMA_VERSION === 1); this is
// where a future v1->v2 transform goes, e.g. splitting a single wallHeight into
// per-edge walls. Each step returns the blob at the NEXT version.
const steps: Record<number, (s: AnySpace) => AnySpace> = {
  // 1: (s) => ({ ...s, /* v1 -> v2 transform */ schemaVersion: 2 }),
};

// Restore edges.length === boundary.length: backfill short arrays with 'none'
// walls, truncate long ones.
function repairEdges(s: AnySpace): void {
  const n = Array.isArray(s.boundary) ? s.boundary.length : 0;
  if (!Array.isArray(s.edges)) s.edges = [];
  while (s.edges.length < n) (s.edges as Edge[]).push({ wall: 'none', height: 0 });
  s.edges.length = n;
}

function migrateNode(raw: AnySpace): AnySpace {
  let s: AnySpace = { ...raw };
  let v: number = typeof s.schemaVersion === 'number' ? s.schemaVersion : 1;

  while (v < SCHEMA_VERSION) {
    const step = steps[v];
    if (!step) throw new Error('No migration from schema v' + v);
    s = step(s);
    v = s.schemaVersion;
  }
  if (v > SCHEMA_VERSION) {
    // File from a newer build. We can't safely down-migrate; refuse loudly.
    throw new Error('Space schema v' + v + ' is newer than this app');
  }

  s.schemaVersion = SCHEMA_VERSION;
  repairEdges(s);
  if (Array.isArray(s.zones)) s.zones = s.zones.map(migrateNode); // zones are Spaces
  return s;
}

// The export that store.ts re-exports as `migrate`.
export function migrate(raw: AnySpace): Space {
  return migrateNode(raw) as Space;
}
ids without a librarycrypto.randomUUID() is a built-in on window.crypto (and Node 19+) that returns an RFC 4122 v4 UUID string — no uuid package needed. It requires a secure context (HTTPS or localhost), which Vite's dev server and any real deployment both satisfy, and it is also available inside Web Workers (relevant for the grid worker in Section B·8). If you ever need a fallback for an insecure origin, crypto.getRandomValues(new Uint8Array(16)) plus manual hex formatting (set the version nibble to 4 and the variant bits to 10) gets you there, but you almost certainly won't.

With types.ts, store.ts, and migrate.ts, the editor and studio share one durable contract. The editor only ever calls SpaceStore.save; the studio only ever calls SpaceStore.load then buildGridSeries (Section B·6). Nothing derived touches disk, every read is migration-safe (root and zones alike), and a space is portable as a single human-readable JSON file with zero dependencies. B·2Canvas core

A canvas you can build on

The editor and the studio look like different apps — one lets you drag walls into existence, the other animates a sun across a finished scene — but they draw onto the same canvas substrate. Both need world metres mapped to screen pixels with north up, both need crisp rendering on Retina displays, both need to translate a finger or mouse position back into the local-metre coordinate space the Space model speaks. This section is the canonical home for that substrate: the fitted transform makeT, its inverse toWorld, the Viewport that layers pan/zoom on top, and a small kit of pointer and hit-test helpers (distanceToSegment lives here too — the engine in Section B·6 imports it). The two surfaces just disagree about *when* to redraw.

makeT does the hard half: it derives a Space's world bounds straight from space.boundary (there is no world field on Space — never invent one), fits them into the canvas with padding, centres the result, and flips the y-axis so north is up. It returns the transform as a set of closures — X, Y, S plus the raw scale and the canvas-space centre cx/cy — and nothing reaches inside it. The inverse, toWorld, is expressed purely in terms of that public surface (T.X, T.Y, T.scale), so the two stay perfect inverses by construction. Viewport then composes makeT and toWorld and adds a user-controlled zoom and pixel panX/panY — it does not re-derive the transform.

Read it top to bottom for drawing (Viewport.worldToScreen) and bottom to top for input (Viewport.screenToWorld). The crucial discipline: all geometry, hit-testing and the Space model stay in world metres; pixels exist only at the canvas boundary. That keeps shadow math, distances and thresholds physically meaningful regardless of zoom. And there is exactly one transform module — makeT/toWorld/Viewport — that the editor (B·3/B·4), the map-image calibration (B·5), the engine (B·6) and the studio (B·7) all import from here.

makeT and toWorld: the fitted transform and its inverse

transform.ts 
import type { Space, Vec2 } from './model'; // model + types: Section B·1

// The canonical fitted transform. Bounds come from space.boundary — there is
// NO world field on Space. North is up: Y flips so larger world-y sits higher.
// Returns closures (X/Y/S) plus the raw scale and the canvas-space centre.
// ox/oy are CLOSED OVER and never exposed; toWorld recovers everything it
// needs from the public X/Y/scale, so the pair stay exact inverses.
export interface T {
  scale: number;            // world metres -> CSS px (at zoom 1)
  X(x: number): number;     // world x (metres) -> CSS px
  Y(y: number): number;     // world y (metres) -> CSS px (north up)
  S(m: number): number;     // a world LENGTH (metres) -> CSS px
  cx: number; cy: number;   // canvas-space centre of the fitted box
}

export function makeT(space: Space, CW: number, CH: number, padM = 1): T {
  const xs = space.boundary.map(p => p.x), ys = space.boundary.map(p => p.y);
  const minX = Math.min(...xs) - padM, maxX = Math.max(...xs) + padM;
  const minY = Math.min(...ys) - padM, maxY = Math.max(...ys) + padM;
  const ww = maxX - minX, wh = maxY - minY, pad = 24;
  const scale = Math.min((CW - 2 * pad) / ww, (CH - 2 * pad) / wh);
  const ox = (CW - ww * scale) / 2, oy = (CH - wh * scale) / 2;
  return {
    scale,
    X: (x: number) => ox + (x - minX) * scale,
    Y: (y: number) => oy + (maxY - y) * scale, // flip -> north up
    S: (m: number) => m * scale,
    cx: ox + ww * scale / 2,
    cy: oy + wh * scale / 2,
  };
}

// Inverse uses ONLY the public T (no leaked ox/oy). Because X(x) = ox + (x-minX)*scale,
// X(0) = ox - minX*scale, so x = (sx - X(0))/scale. Y flips, so y = (Y(0) - sy)/scale.
export function toWorld(T: T, sx: number, sy: number): Vec2 {
  return { x: (sx - T.X(0)) / T.scale, y: (T.Y(0) - sy) / T.scale };
}

The Viewport: composes makeT, layers pan/zoom

viewport.ts 
import { makeT, toWorld, T } from './transform';
import type { Space, Vec2 } from './model';

// Viewport COMPOSES the fitted transform and layers pan (CSS px) + zoom
// (multiplier) on top. It does NOT redefine the world->canvas math — that
// lives in makeT/toWorld above. Recompute T on resize or space change.
export class Viewport {
  T: T;
  panX = 0;
  panY = 0;
  zoom = 1;

  constructor(space: Space, CW: number, CH: number) {
    this.T = makeT(space, CW, CH);
  }

  refit(space: Space, CW: number, CH: number) { this.T = makeT(space, CW, CH); }

  // WORLD metres -> CSS pixels: pan/zoom applied on top of the fitted T.
  worldToScreen(p: Vec2): Vec2 {
    return {
      x: this.panX + this.zoom * this.T.X(p.x),
      y: this.panY + this.zoom * this.T.Y(p.y),
    };
  }

  // CSS pixels -> WORLD metres: undo pan/zoom, then the public inverse.
  screenToWorld(sx: number, sy: number): Vec2 {
    return toWorld(this.T, (sx - this.panX) / this.zoom, (sy - this.panY) / this.zoom);
  }

  // A SCREEN length in px -> metres. NOTE the name: this is the screen-space
  // bridge for pick tolerances. Image-pixel -> world metres is a DIFFERENT
  // operation called imagePxToWorld(pImg, calibration) and lives in Section B·5.
  pxToMetres(lenPx: number): number { return lenPx / (this.zoom * this.T.scale); }

  // Zoom toward a screen anchor so the point under the cursor stays put.
  zoomAt(anchor: Vec2, factor: number, min = 0.25, max = 12) {
    const before = this.screenToWorld(anchor.x, anchor.y);
    this.zoom = Math.min(max, Math.max(min, this.zoom * factor));
    const after = this.worldToScreen(before);
    this.panX += anchor.x - after.x;
    this.panY += anchor.y - after.y;
  }
}
Keep the y-flip honestThe fastest way to ship a subtle drift bug is to get the north-up flip wrong in one direction. makeT computes Y(y) = oy + (maxY - y)*scale — bigger world-y maps to a smaller screen-y, i.e. higher up. toWorld undoes exactly that with y = (T.Y(0) - sy)/T.scale. Because toWorld is written against the *public* T.X/T.Y/T.scale rather than re-deriving offsets, the round-trip is correct by construction. Still, before you build anything on top: write a unit test asserting screenToWorld(worldToScreen(p)) ≈ p for several points at several zoom/pan settings, and a second test pinning a known corner — the north-east boundary vertex (max x, max y) must land near the top-right of the fitted box. A round-trip test alone won't catch a flip that's self-consistent but upside down.

Hi-DPI sizing: devicePixelRatio + ResizeObserver

A canvas has two sizes: its CSS box (what the user sees, what Pointer Events measure in) and its backing buffer (canvas.width/height in device pixels). For crisp lines you size the buffer to CSS × devicePixelRatio, then call ctx.setTransform(dpr,0,0,dpr,0,0) once so all your draw calls keep using CSS-pixel coordinates while the GPU renders at full density. Wrap the whole thing in a ResizeObserver so a window resize, sidebar toggle, or orientation change refits without a layout-thrashing window.resize listener. The onResize(cssW, cssH) callback is also where you call viewport.refit(space, cssW, cssH).

resize.ts 
// Returns a disposer. Calls onResize(cssW, cssH) after the buffer is
// (re)sized and the dpr transform applied. Safe to call repeatedly.
export function attachHiDpiResize(
  canvas: HTMLCanvasElement,
  ctx: CanvasRenderingContext2D,
  onResize: (cssW: number, cssH: number) => void,
): () => void {
  const apply = () => {
    const rect = canvas.getBoundingClientRect();
    const cssW = Math.max(1, Math.round(rect.width));
    const cssH = Math.max(1, Math.round(rect.height));
    const dpr = Math.min(window.devicePixelRatio || 1, 2); // cap at 2: 3x is wasted fill-rate
    const bw = Math.round(cssW * dpr), bh = Math.round(cssH * dpr);
    const sizeChanged = canvas.width !== bw || canvas.height !== bh;
    if (sizeChanged) {
      canvas.width = bw;   // assigning width/height RESETS all context state
      canvas.height = bh;
      // The reset above clears the transform back to identity, so the dpr
      // scale must be re-applied whenever we touched the buffer size.
      ctx.setTransform(dpr, 0, 0, dpr, 0, 0);
    }
    onResize(cssW, cssH);
  };

  const ro = new ResizeObserver(apply);
  ro.observe(canvas);
  apply(); // initial pass
  return () => ro.disconnect();
}
Why cap dpr at 2Phones report devicePixelRatio of 3+. A balcony plan has no sub-pixel detail that benefits, and a 3× buffer is 2.25× the fill-rate of a 2× one — which matters in the studio's rAF loop (see Section B·7 and the useAnimationFrame hook in Phase 08). Capping at 2 is the standard map/canvas trade-off. Setting canvas.width (even to the same value) wipes the context and resets its transform to identity, so we guard the assignment behind a size-changed check to avoid needless clears, and re-apply setTransform(dpr,0,0,dpr,0,0) whenever we did resize.

Two render strategies, one substrate

The substrate is identical; the scheduling differs. The editor is event-driven: it only redraws when something actually changed — a pointer moved a vertex, the zoom changed, a wall toggled. A persistent rAF loop there would burn battery redrawing a static plan 60 times a second. The studio is the opposite: the sun is continuously moving, so it runs the useAnimationFrame loop from Phase 08 (delta-time stepping, see Appendix A·3). Both share the same draw routine, which is just clear → draw layers in order.

  };

Pointer Events: client coords → canvas → world

Pointer Events unify mouse, touch and stylus into one stream, which is exactly what an editor that must work on phone and desktop wants. The pattern is: on pointerdown, call setPointerCapture(e.pointerId) so you keep receiving pointermove/pointerup even if the finger slides off the canvas; convert clientX/clientY to canvas-local CSS pixels by subtracting getBoundingClientRect(); then hand that pair to vp.screenToWorld(sx, sy). We cache the rect at gesture start — reading it per-move forces layout.

pointer.ts 
import type { Viewport } from './viewport';
import type { Vec2 } from './model';

export interface DragHandlers {
  onDown?(world: Vec2, e: PointerEvent): void;
  onMove?(world: Vec2, e: PointerEvent): void;
  onUp?(world: Vec2, e: PointerEvent): void;
}

export function attachPointer(
  canvas: HTMLCanvasElement, vp: Viewport, h: DragHandlers,
): () => void {
  let rect: DOMRect | null = null;
  const toWorld = (e: PointerEvent): Vec2 => {
    const r = rect ?? canvas.getBoundingClientRect();
    return vp.screenToWorld(e.clientX - r.left, e.clientY - r.top);
  };

  const down = (e: PointerEvent) => {
    rect = canvas.getBoundingClientRect();   // cache once per gesture
    canvas.setPointerCapture(e.pointerId);   // keep events if pointer leaves canvas
    h.onDown?.(toWorld(e), e);
  };
  const move = (e: PointerEvent) => { if (rect) h.onMove?.(toWorld(e), e); };
  const up = (e: PointerEvent) => {
    h.onUp?.(toWorld(e), e);
    if (canvas.hasPointerCapture(e.pointerId)) canvas.releasePointerCapture(e.pointerId);
    rect = null;
  };

  canvas.addEventListener('pointerdown', down);
  canvas.addEventListener('pointermove', move);
  canvas.addEventListener('pointerup', up);
  canvas.addEventListener('pointercancel', up);
  // Stop the browser scrolling/zooming the page when dragging on the canvas.
  canvas.style.touchAction = 'none';

  return () => {
    canvas.removeEventListener('pointerdown', down);
    canvas.removeEventListener('pointermove', move);
    canvas.removeEventListener('pointerup', up);
    canvas.removeEventListener('pointercancel', up);
  };
}
touch-action: none is mandatoryWithout touchAction = 'none' on the canvas, the browser claims vertical drags for page scroll and two-finger gestures for pinch-zoom, and your pointermove stream goes silent mid-gesture. Set it in CSS or JS, but set it. On desktop you'll also want e.preventDefault() on a wheel handler if you wire vp.zoomAt to the scroll wheel — and register that wheel listener with { passive: false }, because Chrome treats wheel listeners as passive by default and silently ignores preventDefault() otherwise; without it the page scrolls underneath the zoom.

Hit-testing in world metres

The editor constantly asks geometric questions: is the pointer near *this* vertex so I can drag it? near *that* edge so I can insert a vertex or toggle a wall? These reduce to two primitives — point-to-point distance and distanceToSegment (point-to-segment with endpoint clamping) — both computed in world metres, so a single physical pick tolerance behaves the same at every zoom. distanceToSegment is defined here and imported by the engine's microclimate in Section B·6 — do not duplicate it there. The bridge from pixels to metres is vp.pxToMetres: a comfortable ~12px touch target becomes vp.pxToMetres(12) metres of tolerance. For interior containment use pip (ray casting, even-odd) from Appendix A·4 — imported, not re-derived here.

hittest.ts 
import type { Vec2, Space } from './model';
import type { Viewport } from './viewport';

export function distanceToPoint(p: Vec2, q: Vec2): number {
  return Math.hypot(p.x - q.x, p.y - q.y);
}

// Shortest distance from point p to segment ab. Projects p onto the infinite
// line, clamps the parameter to [0,1] so it stays on the segment, then measures
// to that clamped foot. All in world metres. Imported by microclimate (B·6).
export function distanceToSegment(p: Vec2, a: Vec2, b: Vec2): number {
  const abx = b.x - a.x, aby = b.y - a.y;
  const len2 = abx * abx + aby * aby;
  if (len2 === 0) return distanceToPoint(p, a); // degenerate: a == b
  let t = ((p.x - a.x) * abx + (p.y - a.y) * aby) / len2;
  t = Math.max(0, Math.min(1, t));              // clamp onto the segment
  const fx = a.x + t * abx, fy = a.y + t * aby; // foot of perpendicular
  return Math.hypot(p.x - fx, p.y - fy);
}

export interface Hit {
  kind: 'vertex' | 'edge';
  index: number;        // boundary vertex index, or edge start-vertex index
  distM: number;        // distance in metres (for tie-breaking)
}

// Pick the nearest vertex first, else nearest edge, within a pixel threshold.
// Vertices win ties because the user usually wants to grab a corner.
export function hitTest(
  worldPt: Vec2, space: Space, vp: Viewport, thresholdPx = 12,
): Hit | null {
  const tol = vp.pxToMetres(thresholdPx); // px tolerance -> metres at this zoom
  const verts = space.boundary;
  const n = verts.length;
  if (n === 0) return null;

  let bestV: Hit | null = null;
  for (let i = 0; i < n; i++) {
    const d = distanceToPoint(worldPt, verts[i]);
    if (d <= tol && (!bestV || d < bestV.distM))
      bestV = { kind: 'vertex', index: i, distM: d };
  }
  if (bestV) return bestV; // corner takes priority

  let bestE: Hit | null = null;
  for (let i = 0; i < n; i++) {
    const a = verts[i], b = verts[(i + 1) % n]; // closed ring
    const d = distanceToSegment(worldPt, a, b);
    if (d <= tol && (!bestE || d < bestE.distM))
      bestE = { kind: 'edge', index: i, distM: d };
  }
  return bestE;
}
Why pixel thresholds, world mathThe tolerance is expressed in pixels because that's what 'feels close' to a human regardless of how zoomed in they are — a finger is ~10–12px wide on any screen. But the comparison happens in metres so the distance functions are reusable by the sun engine and the grid (which think only in metres — see Section B·6). vp.pxToMetres does the one conversion at the boundary: tol = vp.pxToMetres(thresholdPx). Zoom in and that tolerance shrinks in metres, so you can pick a vertex from a much smaller physical radius; that's correct — the user sees it bigger, so they aim better. Keep this distinct from imagePxToWorld (Section B·5), which converts *image* pixels of a calibrated base photo, not *screen* pixels.

B·3Editor: shape

Drawing the boundary

Everything downstream depends on one polygon. The boundary: Vec2[] is the spine of a Space — buildGridSeries rasterizes inside it (see Section B·6), the sun sim casts shadows across it, the plant matcher reads cells inside it. So the editor's first job is to let someone author and revise that ring of points in local metres (+x east, +y north) with their finger or mouse, while we keep the data clean enough that the rest of the engine never has to special-case it.

We keep this deliberately plain: a useReducer holds the document (the Space being edited plus a transient closed flag that never persists into the Space), a tiny useState holds the tool (select | draw | addVertex), and pointer handlers translate screen pixels back into world metres before dispatching an action. Because the boundary is always a free polygon — never a sealed "rectangle" type — irregular plots like the land scene (a six-point trace) and a tidy balcony rectangle are the *same* code path. The rectangle is just a seed, not a special shape (tie back to the one-Space reframe in Phase 00).

The tool state machine

Three modes, and the transitions between them are explicit. select is the resting state: you drag vertices, click an edge (with addVertex armed) to splice in a point, or tap a vertex to delete it. draw appends a new vertex on each canvas click and the loop stays open until you click the first vertex (or press Enter) to CLOSE it. addVertex is a one-shot: arm it, click an edge, drop a point projected onto that edge, fall back to select. Keeping the machine this small means every pointer event has exactly one meaning given the current mode — no modifier-key guessing.

Pixels to metres: using B·2's transform

makeT, toWorld, and Viewport are defined in Section B·2 — we only consume them here. The editor builds a Viewport(space, CW, CH) (which composes makeT internally and layers pan/zoom on top), then runs every pointer event through vp.screenToWorld(sx, sy) to get world metres. The one subtlety that decides the whole round trip: in the prototype CW/CH are CSS pixels, the backing store is sized CW*dpr × CH*dpr, and the draw context runs ctx.setTransform(dpr,0,0,dpr,0,0) so every draw call is in CSS px. That means makeT's scale is CSS px per metre, not device px. Pointer events also arrive in CSS (client) px, and getBoundingClientRect() returns CSS px — so the two spaces already match and no DPR factor enters the inversion. We subtract only the rect origin to get a canvas-local screen px, then hand that to Viewport.screenToWorld.

Multiplying the pointer by dpr would double-count it and place clicks at the wrong metres on any HiDPI screen. Keep pointer math entirely in CSS px — it round-trips exactly against makeT. The document reducer + actions

All boundary mutations go through one reducer so undo/redo (below) can snapshot a single source of truth. Each action carries the world-space point (already converted via B·2) or an index. INSERT_VERTEX is the only one that needs geometry beyond array splicing — the caller projects the click onto the hit edge so the new vertex lands *on* the polygon, and passes that projected point in. projectToEdge is exported here and reused by the pointer layer; the reducer itself stays a pure switch. (Note newSpace(type) from B·1 seeds an empty boundary: [] — the editor opens on that and grows it.)

editorReducer.ts — boundary actions 
import type { Space, Vec2 } from './model';   // B·1

export type Action =
  | { kind: 'ADD_VERTEX'; p: Vec2 }                     // append (draw mode)
  | { kind: 'MOVE_VERTEX'; i: number; p: Vec2 }         // drag
  | { kind: 'INSERT_VERTEX'; edge: number; p: Vec2 }    // splice after edge-start i
  | { kind: 'DELETE_VERTEX'; i: number }
  | { kind: 'CLOSE' }                                   // finish draw; marks closed
  | { kind: 'SEED_RECT'; w: number; h: number };        // balcony starter

// `closed` is editor-local transient state; it is NOT part of the persisted
// Space (the Space schema in B·1 has no `closed` field — a boundary is always
// a ring). Persistence is SpaceStore.save(doc.space), defined in B·1.
export interface EditorDoc { space: Space; closed: boolean; }

const dot = (a: Vec2, b: Vec2) => a.x * b.x + a.y * b.y;

/** nearest point ON segment a->b to p, clamped to the segment ends */
export function projectToEdge(p: Vec2, a: Vec2, b: Vec2): Vec2 {
  const ab = { x: b.x - a.x, y: b.y - a.y };
  const ap = { x: p.x - a.x, y: p.y - a.y };
  const len2 = dot(ab, ab) || 1e-9;                      // guard zero-length edge
  let t = dot(ap, ab) / len2;                            // param along the edge
  t = Math.max(0, Math.min(1, t));                       // clamp to [0,1]
  return { x: a.x + ab.x * t, y: a.y + ab.y * t };
}

export function reducer(doc: EditorDoc, a: Action): EditorDoc {
  const b = doc.space.boundary;
  switch (a.kind) {
    case 'ADD_VERTEX':
      return setBoundary(doc, [...b, a.p]);

    case 'MOVE_VERTEX': {
      if (a.i < 0 || a.i >= b.length) return doc;
      const next = b.slice();
      next[a.i] = a.p;
      return setBoundary(doc, next);
    }
    case 'INSERT_VERTEX': {                              // edge = index of start vertex
      const next = b.slice();
      next.splice(a.edge + 1, 0, a.p);                   // new vertex after start
      return setBoundary(doc, next);
    }
    case 'DELETE_VERTEX': {
      if (b.length <= 3) return doc;                     // a polygon needs >= 3
      return setBoundary(doc, b.filter((_, i) => i !== a.i));
    }
    case 'CLOSE':
      return b.length >= 3 ? { ...doc, closed: true } : doc;

    case 'SEED_RECT': {
      // CCW in metres so shoelace area is positive; origin at the SW corner.
      // Walk E -> N -> W -> S with +y up = counter-clockwise.
      const rect: Vec2[] = [
        { x: 0, y: 0 }, { x: a.w, y: 0 },
        { x: a.w, y: a.h }, { x: 0, y: a.h },
      ];
      return { ...doc, closed: true, space: { ...doc.space, boundary: rect } };
    }
    default:
      return doc;
  }
}

function setBoundary(doc: EditorDoc, boundary: Vec2[]): EditorDoc {
  return { ...doc, space: { ...doc.space, boundary } };
}
INSERT_VERTEX edge indexedge is the index of the segment's start vertex (segment i runs from boundary[i] to boundary[(i+1) % n]). Splicing the projected point at edge + 1 puts it between the two endpoints in winding order, so the polygon stays simple and the winding (CCW) is preserved.

Snapping: vertex, right-angle, and grid

Raw pointer coords are jittery and people want clean numbers. snap() runs three rules in priority order and returns the world point plus a tag so the canvas can draw feedback. Vertex snap wins first (magnet to an *existing other* corner within a screen-space radius — it must skip the vertex currently being dragged, or that vertex would magnet to itself and freeze). Right-angle snap is next while drawing: if the candidate edge from the previous vertex is within a few degrees of parallel/perpendicular to the *previous* edge, lock it to exactly 0/90/180/270° by projecting onto that axis. Grid snap is the fallback: round to the nearest 0.1 m. Convert pixel radii to metres with Viewport.pxToMetres (B·2) so the magnet feels the same at any zoom.

snap.ts — three rules, priority ordered 
import type { Vec2 } from './model';      // B·1
import { Viewport } from './viewport';    // B·2 — pxToMetres lives here

export interface Snap { p: Vec2; kind: 'vertex' | 'angle' | 'grid'; ref?: Vec2; }

const GRID_M = 0.1;            // metric grid step (m)
const VERTEX_PX = 12;          // magnet radius to existing corners (CSS px)
const ANGLE_TOL = 6;          // degrees from 0/90/180/270 to lock an edge

const roundTo = (v: number, step: number) => Math.round(v / step) * step;
const snapGrid = (p: Vec2): Vec2 => ({ x: roundTo(p.x, GRID_M), y: roundTo(p.y, GRID_M) });

/** Signed angular difference in [-PI, PI], correct for any sign of input. */
const wrapAngle = (d: number) => Math.atan2(Math.sin(d), Math.cos(d));

export function snap(
  p: Vec2,
  boundary: Vec2[],
  vp: Viewport,        // B·2 viewport — used only for pxToMetres (zoom-aware radius)
  opts: {
    prev?: Vec2;       // last committed vertex (draw mode)
    prevPrev?: Vec2;   // the one before it -> defines the reference edge
    skip?: number;     // index of the vertex being dragged (excluded from magnet)
  } = {},
): Snap {
  const { prev, prevPrev, skip } = opts;

  // 1) snap to a nearby EXISTING OTHER vertex (highest priority)
  const rM = vp.pxToMetres(VERTEX_PX);   // CSS-px radius -> metres at current zoom
  let best: { p: Vec2; d: number } | null = null;
  for (let i = 0; i < boundary.length; i++) {
    if (i === skip) continue;                            // never magnet to self
    const v = boundary[i];
    const d = Math.hypot(v.x - p.x, v.y - p.y);
    if (d < rM && (!best || d < best.d)) best = { p: v, d };
  }
  if (best) return { p: best.p, kind: 'vertex', ref: best.p };

  // 2) right-angle lock relative to the previous edge (draw mode only)
  if (prev && prevPrev) {
    const ref = Math.atan2(prev.y - prevPrev.y, prev.x - prevPrev.x);
    const cur = Math.atan2(p.y - prev.y, p.x - prev.x);
    const dist = Math.hypot(p.x - prev.x, p.y - prev.y);
    const tolRad = (ANGLE_TOL * Math.PI) / 180;
    for (const k of [0, 90, 180, 270]) {
      const target = ref + (k * Math.PI) / 180;
      if (Math.abs(wrapAngle(cur - target)) < tolRad) {
        const locked = {
          x: prev.x + Math.cos(target) * dist,
          y: prev.y + Math.sin(target) * dist,
        };
        return { p: locked, kind: 'angle', ref: prev };
      }
    }
  }

  // 3) fall back to the metric grid
  return { p: snapGrid(p), kind: 'grid' };
}
Two snap bugs the naive version hidesFirst: the angular difference MUST wrap with atan2(sin d, cos d) (or add 2π before the modulo). Plain ((cur-target+π) % 2π) - π keeps the sign of the dividend in JS, so when cur-target+π < 0 it returns values like -360°, and a real right-angle candidate is silently missed. Second: the vertex magnet must skip the dragged index — at drag start the cursor sits on that vertex (distance 0 < radius), so without the skip it locks the vertex to its own old position and the handle never moves. Finally, draw the cue: ring around ref on 'vertex', the dashed reference axis from prev on 'angle', the nearest gridlines on 'grid'. A snap you can't see reads as a bug — and keep tolerances small; a magnet that fires from 30 px away is worse than none.

Composing dispatch + history into one editor hook

The reducer is pure and history needs to snapshot whole docs, so we wrap both in a single useEditor hook that is the editor's one source of truth. apply(action) runs the reducer for a live (un-snapshotted) update during a gesture; commit(action) runs the reducer *and* pushes the result onto the undo stack as one step. During a drag we apply every pointermove and commit exactly once on pointerup; in draw mode each click is a commit because each click is a finished gesture. The history stack stores structuredCloned snapshots — a platform builtin, no library — so an in-place tweak can never corrupt a past state. (When the user is done, SpaceStore.save(doc.space) from B·1 persists it.)

useEditor.ts — reducer + snapshot stack, one source of truth 
import { useCallback, useRef, useState } from 'react';
import { reducer, type Action, type EditorDoc } from './editorReducer';

export function useEditor(initial: EditorDoc) {
  const [doc, setDoc] = useState<EditorDoc>(initial);
  const stack = useRef<EditorDoc[]>([structuredClone(initial)]);
  const [index, setIndex] = useState(0);

  /** live, un-recorded update during an in-flight gesture (no undo step) */
  const apply = useCallback((a: Action) => {
    setDoc((d) => reducer(d, a));
  }, []);

  /** run the action AND record the result as exactly one undo step */
  const commit = useCallback((a: Action) => {
    setDoc((d) => {
      const next = reducer(d, a);
      if (next === d) return d;                          // no-op: don't record
      const snap = structuredClone(next);
      stack.current = stack.current.slice(0, index + 1);  // drop redo tail
      stack.current.push(snap);
      setIndex(stack.current.length - 1);
      return next;
    });
  }, [index]);

  const undo = useCallback(() => {
    if (index <= 0) return;
    const i = index - 1;
    setIndex(i);
    setDoc(structuredClone(stack.current[i]));
  }, [index]);

  const redo = useCallback(() => {
    if (index >= stack.current.length - 1) return;
    const i = index + 1;
    setIndex(i);
    setDoc(structuredClone(stack.current[i]));
  }, [index]);

  return {
    doc, apply, commit, undo, redo,
    canUndo: index > 0,
    canRedo: index < stack.current.length - 1,
  };
}
Why apply vs commit (and why snapshots)apply keeps the canvas live every animation frame without polluting history; commit is the only thing that touches the stack, so undo rewinds one *gesture* at a time, never one pixel at a time. The index-as-cursor pattern (decrement to undo, increment to redo, truncate the tail on a fresh edit) is the standard linear-history model. For a single boundary (tens of points) full structuredClone snapshots are simpler and plenty fast; only a many-thousand-point doc would justify switching to a command/inverse-command log to avoid cloning the whole thing each step.

Wiring the pointer handlers

Pointer Events unify mouse/touch/pen, and setPointerCapture is what makes a vertex drag survive the pointer leaving the canvas — capture on pointerdown, every pointermove retargets to us until pointerup. We convert each event to world metres with eventToWorld (which calls B·2's Viewport.screenToWorld). In select mode a pointerdown runs B·2's hitTest (vertex handles first, then edges); a hit vertex arms a drag. A vertex pointerup that never crossed a small drag threshold is a tap → DELETE_VERTEX; one that did is a finished drag → commit. We track total displacement from the down point (not per-event deltas), because a slow drag can move only a pixel or two per event yet travel far overall.

useBoundaryPointer.ts — handlers calling apply / commit 
import { useRef } from 'react';
import { projectToEdge, type Action } from './editorReducer';
import { eventToWorld, clientToCanvasPx } from './editorTransform';  // wraps B·2
import { snap } from './snap';
import { Viewport } from './viewport';   // B·2
import { hitTest } from './hitTest';     // B·2: returns { kind:'vertex'|'edge', i } | null
import type { Vec2 } from './model';     // B·1

type Tool = 'select' | 'draw' | 'addVertex';
const DRAG_PX = 4;   // total movement under this on a vertex = a tap, not a drag

export function useBoundaryPointer(
  canvasRef: React.RefObject<HTMLCanvasElement>,
  getViewport: () => Viewport,            // B·2 viewport (composes makeT)
  getBoundary: () => Vec2[],
  tool: Tool,
  setTool: (t: Tool) => void,
  apply: (a: Action) => void,             // live, no undo step
  commit: (a: Action) => void,            // one undo step
) {
  // track the drag in CSS px so the threshold is screen-space
  const drag = useRef<{ i: number; start: Vec2; moved: boolean } | null>(null);

  function onPointerDown(ev: React.PointerEvent) {
    const c = canvasRef.current!, vp = getViewport();
    const world = eventToWorld(ev.nativeEvent, c, vp);
    const b = getBoundary();
    const hit = hitTest(world, b, vp);   // B·2 hit-testing

    if (tool === 'draw') {
      if (hit?.kind === 'vertex' && hit.i === 0 && b.length >= 3) {
        commit({ kind: 'CLOSE' });
        setTool('select');
        return;
      }
      const prev = b[b.length - 1], prevPrev = b[b.length - 2];
      const s = snap(world, b, vp, { prev, prevPrev });
      commit({ kind: 'ADD_VERTEX', p: s.p });
      return;
    }

    if (tool === 'addVertex' && hit?.kind === 'edge') {
      // project the click onto the hit edge so the point lands ON the line;
      // the projection IS the snap here, so do NOT re-run vertex/grid snap
      // (that could pull it off the edge).
      const a1 = b[hit.i], a2 = b[(hit.i + 1) % b.length];
      const onEdge = projectToEdge(world, a1, a2);
      commit({ kind: 'INSERT_VERTEX', edge: hit.i, p: onEdge });
      setTool('select');
      return;
    }

    if (tool === 'select' && hit?.kind === 'vertex') {
      c.setPointerCapture(ev.pointerId);          // keep events even off-canvas
      drag.current = { i: hit.i, start: clientToCanvasPx(ev.nativeEvent, c), moved: false };
    }
  }

  function onPointerMove(ev: React.PointerEvent) {
    const d = drag.current;
    if (!d) return;
    const c = canvasRef.current!, vp = getViewport();
    const now = clientToCanvasPx(ev.nativeEvent, c);
    // accumulate total displacement from the down point, in CSS px
    if (Math.hypot(now.x - d.start.x, now.y - d.start.y) > DRAG_PX) d.moved = true;
    const world = eventToWorld(ev.nativeEvent, c, vp);
    // live update only — skip the dragged vertex in the magnet scan
    const s = snap(world, getBoundary(), vp, { skip: d.i });
    apply({ kind: 'MOVE_VERTEX', i: d.i, p: s.p });
  }

  function onPointerUp(ev: React.PointerEvent) {
    const d = drag.current;
    drag.current = null;
    if (!d) return;
    canvasRef.current!.releasePointerCapture(ev.pointerId);
    if (d.moved) {
      // re-issue the final position as a single recorded step
      const c = canvasRef.current!, vp = getViewport();
      const world = eventToWorld(ev.nativeEvent, c, vp);
      const s = snap(world, getBoundary(), vp, { skip: d.i });
      commit({ kind: 'MOVE_VERTEX', i: d.i, p: s.p });
    } else {
      commit({ kind: 'DELETE_VERTEX', i: d.i });   // a tap on a vertex deletes it
    }
  }

  return { onPointerDown, onPointerMove, onPointerUp };
}
How a drag becomes one undo stepDuring the drag we only call apply(MOVE_VERTEX) per pointermove, so the canvas tracks the cursor live but nothing is recorded. On pointerup we call commit(MOVE_VERTEX) once with the final snapped position — that is the single history entry for the whole gesture. A tap (no movement past DRAG_PX) takes the other branch and commit(DELETE_VERTEX) instead. Either way exactly one snapshot is pushed per finished gesture.

Area readout — the shoelace formula

Show the live area while editing so people sanity-check against what they measured. The shoelace (Gauss) formula gives a simple polygon's area directly from its vertices. For boundary points (x0,y0)…(x(n-1),y(n-1)) in order, the signed area is A = ½ · Σ (x_i · y_{i+1} − x_{i+1} · y_i) over i = 0…n-1 with indices wrapping (i+1 mod n). Take the absolute value for the displayed area in m²; the sign tells you winding (positive = CCW with +y north up), which is handy to keep consistent for the sun sim. It also doubles as a degenerate-shape guard: an area near 0 means a self-collapsed or collinear polygon.

area.ts — shoelace area + winding 
import type { Vec2 } from './model';   // B·1

/** signed area in m^2; positive = counter-clockwise (with +y = north up) */
export function signedArea(poly: Vec2[]): number {
  let s = 0;
  for (let i = 0, n = poly.length; i < n; i++) {
    const a = poly[i];
    const b = poly[(i + 1) % n];
    s += a.x * b.y - b.x * a.y;     // cross term, indices wrap via % n
  }
  return s / 2;
}

export const area = (poly: Vec2[]) => Math.abs(signedArea(poly));
export const isCCW = (poly: Vec2[]) => signedArea(poly) > 0;

B·4Editor: structures

Walls, doors, obstacles, sky

The boundary (Section B·3) gave you a closed polygon of Vec2 points in local metres. Everything that actually casts shadows lives on top of it: the walls along each edge, the doors punched through them, the obstacles standing inside, and the overhead slab floating above. This phase is the authoring surface — every widget here is a plain canvas hit-test plus a plain <input>, no UI library, and every value you set is written onto the one Space object. The engine (Section B·6) turns that authored Space into shadows: occludersOf(space) is the single adapter that walks your edges, obstacles, and overhead and emits the Occluder list that shadowOf and buildGridSeries consume. This phase never builds occluders itself — it only authors the fields occludersOf reads.

The recurring trick: authoring happens in screen pixels but the model stores world metres, so you constantly round-trip through the transform. World→canvas is Viewport.worldToScreen / T.X,T.Y; pointer→world is Viewport.screenToWorld, which is built on toWorld(T, sx, sy). Both Viewport and toWorld are defined in Section B·2 — import them, do not reimplement. We build five tools in order — edge walls, doors, obstacles, the overhead, and the orientation compass — then close with latitude.

Pointer → world: reuse the Viewport inverse, don't reinvent it

Every editor interaction needs pointer→world. Section B·2 already provides it: Viewport.screenToWorld(sx, sy), which composes toWorld(this.T, ...) and layers pan/zoom on top. toWorld uses only the public transform T — T.X(0), T.Y(0), and T.scale — so there is no need to leak makeT's internal ox/oy/minX/maxY. (An earlier draft of this section extended makeT's return with those internals and re-derived the inverse here; that duplicated B·2 and has been removed.) Your editor holds one Viewport, and the only adapter you write is the canvas-rect / DPR correction below, which maps a raw PointerEvent into the backing-pixel space screenToWorld expects.

src/editor/screen.ts 
import type { Vec2 } from '../model';            // B·1
import { Viewport } from '../view/viewport';      // B·2 (makeT + toWorld + Viewport)

// Map a PointerEvent to canvas BACKING pixels (account for CSS scaling / DPR),
// then defer the actual inversion to the Viewport from B·2.
export function pointerToBackingPx(
  e: PointerEvent,
  canvas: HTMLCanvasElement,
): { sx: number; sy: number } {
  const r = canvas.getBoundingClientRect();
  const sx = (e.clientX - r.left) * (canvas.width / r.width);
  const sy = (e.clientY - r.top) * (canvas.height / r.height);
  return { sx, sy };
}

// The one inversion the editor uses everywhere. No re-derivation: B·2's
// Viewport.screenToWorld -> toWorld(T, ...) already undoes scale + the y flip.
export function eventToWorld(
  e: PointerEvent,
  canvas: HTMLCanvasElement,
  view: Viewport,
): Vec2 {
  const { sx, sy } = pointerToBackingPx(e, canvas);
  return view.screenToWorld(sx, sy);
}

export const dist2 = (a: Vec2, b: Vec2) => (a.x - b.x) ** 2 + (a.y - b.y) ** 2;

Edges: click a wall to cycle full → half → none

edges[i] describes the segment from boundary[i] to boundary[(i+1) % n] — they pair by index, so a 4-point boundary has exactly 4 edges. Hit-testing is *point-to-segment distance*: project the pointer onto each edge and keep the nearest within a metre threshold. Note that distanceToSegment (and the projection it wraps) is a B·2 hit-testing helper — import it; projectToSeg below is the local convenience that also returns the clamped parameter t, which the door tool reuses. On hit, cycle the wall field; height lives in a separate <input type="number"> bound to the selected edge. You author the edge fields here; occludersOf (B·6) is what turns them into shadows — wall:"full" extrudes at full height, wall:"half" at height/2, wall:"none" emits nothing.

src/editor/edges.ts 
import type { Vec2, Edge } from '../model';   // B·1

// Closest point on segment a->b to p, plus the clamped parameter t.
// (distanceToSegment in B·2 wraps the same projection; this also returns t.)
export function projectToSeg(p: Vec2, a: Vec2, b: Vec2) {
  const abx = b.x - a.x, aby = b.y - a.y;
  const len2 = abx * abx + aby * aby || 1e-9;
  const t = Math.max(0, Math.min(1, ((p.x - a.x) * abx + (p.y - a.y) * aby) / len2));
  return { t, point: { x: a.x + t * abx, y: a.y + t * aby } as Vec2 };
}

// Index of the nearest edge within tolM metres, or -1.
export function pickEdge(p: Vec2, boundary: Vec2[], tolM: number): number {
  let best = -1, bestD = tolM * tolM;
  for (let i = 0; i < boundary.length; i++) {
    const a = boundary[i], b = boundary[(i + 1) % boundary.length];
    const { point } = projectToSeg(p, a, b);
    const d = (p.x - point.x) ** 2 + (p.y - point.y) ** 2;
    if (d < bestD) { bestD = d; best = i; }
  }
  return best;
}

const CYCLE = { full: 'half', half: 'none', none: 'full' } as const;
export function cycleWall(edge: Edge): Edge {
  return { ...edge, wall: CYCLE[edge.wall] };
}

Those are render choices you make here. The shadow contribution is not authored in this section — occludersOf(space) in B·6 extrudes each non-none edge into a thin OUTWARD quad of thickness WALL_THICK (0.08 m) at height full ? e.height : e.height/2, tagged kind:"vertical". Doors: drag a marker that stays glued to its edge

A door is stored as door = t in [0,1] — a fraction along the edge, not a coordinate — so it survives the boundary being moved or rescaled. Dragging projects the pointer onto the edge and takes the clamped scalar t = clamp(dot(p−a, b−a) / |b−a|², 0, 1) (vector projection; the maths is in Appendix A·4). t=0 is the start vertex, t=1 the end. To draw the marker, lerp back to world: door_pos = a + t·(b−a), then map through Viewport.worldToScreen.

The door gap is honoured in B·6, not hereA door is a gap in the wall, but this section does not split the wall into pieces. The canonical adapter occludersOf (B·6) currently extrudes one thin quad per edge and reads e.door for the access/door semantics that microclimate uses (door position feeds the access field). If you want light to pass through the gap geometrically, that split belongs in occludersOf (its home), not in a parallel editor function — keep the single adapter authoritative. Author the door fraction here; let B·6 decide how the gap is rasterized. (An earlier draft's wallSpansWithDoor / edgeOccluders have been removed to avoid a second, divergent occluder builder.)

Obstacles & trees: a rectangle, a polygon, or a circle in disguise

An Obstacle is { footprint: Vec2[], height: number, solid?: boolean }. Authoring offers three gestures, all producing the same footprint array: drag a rectangle (two corners → 4 points), click a polygon vertex-by-vertex (close on the first point), or drop a tree — a circle approximated by circlePoly (introduced with the boundary tools in Section B·3). The solid flag is the whole point of the distinction: a solid obstacle (a shed, a raised-bed wall) both casts a shadow *and* excludes its cells from the grid — nothing grows inside a shed. A tree (solid: false) casts a canopy shadow but its cells stay plantable. In buildGridSeries (B·6) that is exactly the split: a cell's inside flag is pip(center, boundary) AND not inside any SOLID occluder, while the shadow sweep applies to *all* occluders regardless of solid.

src/editor/obstacles.ts 
import type { Vec2, Obstacle } from '../model';   // B·1
import { circlePoly } from './boundary';          // B·3

// Rectangle from two dragged corners (any order). North is up, so y0 < y1
// means y0 is the SOUTH edge. Returns a CCW footprint in world metres.
export function rectFootprint(p0: Vec2, p1: Vec2): Vec2[] {
  const x0 = Math.min(p0.x, p1.x), x1 = Math.max(p0.x, p1.x);
  const y0 = Math.min(p0.y, p1.y), y1 = Math.max(p0.y, p1.y);
  return [{ x: x0, y: y0 }, { x: x1, y: y0 }, { x: x1, y: y1 }, { x: x0, y: y1 }];
}

export function makeBox(p0: Vec2, p1: Vec2, height: number): Obstacle {
  return { footprint: rectFootprint(p0, p1), height, solid: true };
}

// A tree: canopy radius r, trunk at (cx,cy), height = canopy top. NOT solid:
// its cells stay plantable even though it casts a canopy shadow.
export function makeTree(cx: number, cy: number, r: number, height: number): Obstacle {
  return { footprint: circlePoly(cx, cy, r, 14), height, solid: false };
}

// Polygon authoring: accumulate clicks; close when one lands near the first.
export function tryClosePolygon(
  pts: Vec2[], click: Vec2, snapM: number, height = 2,

  if (pts.length >= 3) {
    const d = (pts[0].x - click.x) ** 2 + (pts[0].y - click.y) ** 2;
    if (d <= snapM * snapM) return { footprint: pts.slice(), height, solid: true };
  }
  return null;
}

The overhead slab: shadow is TRANSLATE-ONLY (and that branch lives in B·6)

An Overhead is { footprint, height } where height is the clearance — how high the slab floats above the floor (a balcony soffit, a pergola roof, an upstairs balcony). Authoring is identical to a polygon obstacle, but it writes to space.overhead, not the obstacles array, and you render it as a dashed outline so the user reads it as "above you, not on the ground." The reason it gets its own type is the shadow math, which is handled by shadowOf in B·6: it branches on occ.kind. A kind:"vertical" occluder returns the convex hull of footprint plus translated copy (the wall body sweeps the ground); a kind:"overhead" occluder is translated only by L = clearance/tan(alt) opposite the sun — no hull. occludersOf(space) tags the overhead as kind:"overhead", so you never call a shadow function here; you only author the footprint and clearance.

Why a soffit shades the BACK of a balconyIntuition says a roof shades what is directly under it. But shadowOf offsets the footprint *opposite the sun*. On a north-opening balcony (S-hemisphere, sun in the north), the sun comes from the open side, so the soffit's translated footprint lands toward the back wall — the recessed rear gets shade most of the day while the front rail bakes. Orientation: a custom canvas compass dial

geo.bearing is the rotation between local north (+y) and true north, in radians, measured clockwise from north. Rather than a number field, draw a compass dial: a circle with an N tick and a draggable needle. On pointermove, take the vector from the dial centre to the pointer and read its angle. The axis subtlety: screen atan2(dy, dx) measures from +x (east) growing *clockwise on screen* (y is down). We want a bearing measured clockwise from north, so use bearing = atan2(dx, -dy) — feeding dx as the opposite and -dy (up = north) as the adjacent rotates the zero to the top and makes clockwise positive. Normalise into [0, 2π). This bearing is read by sunAt in B·6: the sun's ground direction is rotated by -space.geo.bearing into the local frame (one rotation; see Appendix A·2).

      deg = (360 - e.alpha) % 360;   // alpha is CCW from north -> flip to CW
    } else {

    }

    });

    window.addEventListener('deviceorientation', handler);
  }
  return () => window.removeEventListener('deviceorientation', handler);
}

Latitude: one number that bends the whole arc

geo.lat is a plain <input type="number" min="-90" max="90" step="0.1">, or it falls out of the map georef automatically (see Section B·5: two lat/lng tie-points give you a coordinate, and its latitude seeds this field). It is the most consequential value on the page even without a widget of its own: latitude sets the peak altitude and the azimuth sweep of the sun's path. Near the equator the sun climbs near-vertical and the day is ~12 h year-round; toward the poles the arc flattens and summer/winter diverge hard. sunAt(dayOfYear, hour, latRad) (B·6) consumes latRad = space.geo.lat * PI/180 directly to compute declination (Cooper) and hour angle (the maths is Appendix A·2). When lat changes, buildGridSeries (B·6) re-integrates sun-hours across SEASONS, so the heatmap visibly redraws as you nudge the field — the cheapest possible way to make latitude *feel* load-bearing.

Trace it on a real map

A balcony you can pace out by hand; a garden or a half-acre plot you cannot. For anything bigger than a room the honest move is to trace it over a real top-down image — a satellite screenshot, a site plan, a survey PDF. The whole trick is doing this with *zero* map libraries: no slippy tiles, no Leaflet, no Mapbox. The image is just pixels you drawImage onto the base layer, and your job is to learn the one number that turns pixels into metres — metresPerPixel — so every boundary point, obstacle, and shadow you trace afterwards lands in the same local-metres coordinate system the rest of the engine already speaks (Vec2, +x east, +y north; the world->canvas transform makeT lives in Section B·2 and the engine in Section B·6).

The pipeline has four moving parts: load the image into a dataUrl and an Image; calibrate scale by dragging one segment over a feature of known real length; optionally georeference with two lat/lng points so the trace inherits a true bearing; then trace boundary and obstacles with the same B·3/B·4 tools — now reading out in metres. Everything is persisted in Space.base through the one SpaceStore module (Section B·1); this section never opens a second persistence path except the canon-blessed IndexedDB option for oversized images. (LatLng here is { lat: number, lng: number }, the shape BaseImage.georef = { a: LatLng, b: LatLng } uses.)

Read it left to right. Pixel -> metres is the load-bearing step and needs nothing but the calibration segment. Metres -> lat/lng is optional — you only need it for a true compass bearing (which feeds space.geo.bearing and the solar maths, Appendix A·2) or to drop the space on a real map later. The equirectangular toLocalMetres(p, ref) is the projection from Appendix A·2; here we add a 2-point similarity transform that ties the *image* to those world coordinates.

1 . Load the image -> dataUrl -> base layer

Accept the image two ways — a file picker (<input type=file accept="image/*">) and drag/drop onto the stage. Both end at the same place: a File, which FileReader.readAsDataURL turns into a base64 dataUrl. We keep that string (it is what we persist as Space.base.dataUrl) and also decode it into an HTMLImageElement for the natural pixel dimensions used by the initial fit. Downscale anything huge before storing — see the storage note in step 5.

loadBaseImage.ts 
// File -> dataUrl -> decoded Image. Returns both: dataUrl to persist, img to draw.
export async function fileToBaseImage(
  file: File,
  maxEdgePx = 1600,          // downscale guard for the ~5MB localStorage budget
): Promise<{ dataUrl: string; img: HTMLImageElement; w: number; h: number }> {
  const rawUrl = await new Promise<string>((res, rej) => {
    const fr = new FileReader();
    fr.onload = () => res(fr.result as string);
    fr.onerror = () => rej(fr.error);
    fr.readAsDataURL(file);            // -> "data:image/png;base64,...."
  });

  const img = await decode(rawUrl);
  const longEdge = Math.max(img.naturalWidth, img.naturalHeight);
  if (longEdge <= maxEdgePx) {
    return { dataUrl: rawUrl, img, w: img.naturalWidth, h: img.naturalHeight };
  }
  // re-encode at a capped size so a 12 MP phone shot fits the blob budget
  const k = maxEdgePx / longEdge;
  const w = Math.round(img.naturalWidth * k), h = Math.round(img.naturalHeight * k);
  const off = document.createElement('canvas');
  off.width = w; off.height = h;
  off.getContext('2d')!.drawImage(img, 0, 0, w, h);
  const dataUrl = off.toDataURL('image/jpeg', 0.82);   // jpeg: photos compress far smaller than png
  return { dataUrl, img: await decode(dataUrl), w, h };
}

function decode(url: string): Promise<HTMLImageElement> {
  return new Promise((res, rej) => {
    const im = new Image();
    im.onload = () => res(im);
    im.onerror = () => rej(new Error('image decode failed'));
    im.src = url;        // data: URLs are same-origin, no crossOrigin / canvas-taint issues
  });
}

2 . Scale calibration — the one number that matters

The user finds any feature whose real length they know — a 10 m fence run, the scale bar baked into a satellite screenshot, a standard garage door, a surveyed building edge — and drags a segment over it with two pointer taps (reuse the B·3 pointer-tap handler). They type the real length in metres. That is the entire UI. The maths is one division: metresPerPixel = realMetres / pixelLength. The longer the calibration segment, the smaller the per-pixel error, so coach the user toward the longest known feature in frame. The result populates Space.base.calibration — the canonical BaseImage shape from Section B·1.

calibration.ts 
import type { Vec2, BaseImage } from './model';   // model types: Section B.1

// Two endpoints picked ON THE IMAGE, in *image pixels* (not screen pixels --
// convert through Viewport.screenToWorld's inverse first, see the shaded note).
export function calibrateScale(
  aPx: Vec2, bPx: Vec2,         // segment dragged over the known feature
  realMetres: number,          // what the user typed, e.g. 10
  originPx: Vec2 = aPx,         // pixel that maps to local (0,0); default = segment start
): BaseImage['calibration'] {
  const dx = bPx.x - aPx.x, dy = bPx.y - aPx.y;
  const pixelLength = Math.hypot(dx, dy);
  if (pixelLength < 1) throw new Error('calibration segment too short');
  return {
    metresPerPixel: realMetres / pixelLength,   // <-- the whole game
    originPx,
    rotationRad: 0,            // 0 until georeferenced (step 3). Image +x is treated as east.
  };
}

// THE canonical image-pixel -> world-metres transform (the name resolved in the
// canon NAMING section: imagePxToWorld, NOT pxToMetres -- pxToMetres is a SCREEN
// length on Viewport, Section B.2, a different thing). EVERY later trace flows here.
// Image y grows downward; local +y is north -> we flip y (originPx.y - px.y).
export function imagePxToWorld(pImg: Vec2, cal: BaseImage['calibration']): Vec2 {
  const k = cal.metresPerPixel;
  const ex = (pImg.x - cal.originPx.x) * k;       // east offset in metres
  const ny = (cal.originPx.y - pImg.y) * k;       // north offset (origin - px, the flip)
  if (!cal.rotationRad) return { x: ex, y: ny };
  // if georeferenced, rotate local axes onto true north (CCW by rotationRad):
  const c = Math.cos(cal.rotationRad), s = Math.sin(cal.rotationRad);
  return { x: ex * c - ny * s, y: ex * s + ny * c };
}

// Exact inverse of imagePxToWorld: world metres -> image pixel (for re-drawing handles).
export function worldToImagePx(m: Vec2, cal: BaseImage['calibration']): Vec2 {
  let ex = m.x, ny = m.y;
  if (cal.rotationRad) {                          // undo the rotation first (rotate by -theta)
    const c = Math.cos(-cal.rotationRad), s = Math.sin(-cal.rotationRad);
    [ex, ny] = [m.x * c - m.y * s, m.x * s + m.y * c];
  }
  const k = cal.metresPerPixel;
  return { x: cal.originPx.x + ex / k, y: cal.originPx.y - ny / k };   // unflip y
}
Screen pixels are not image pixelsPointer taps arrive in screen coordinates, which depend on the current pan/zoom of the Viewport (Section B·2). Calibration must be stored in image pixels so it survives a re-zoom and reload. Convert at capture time using the same Viewport: world = view.screenToWorld(sx, sy) gives metres, and if the base is uncalibrated you instead invert the contain-fit (imgPx = (screenPt - fitOffset) / fitScale). Store originPx and the calibration endpoints in image space; never persist a screen-space coordinate — the canvas size changes between devices. Do not reach for Viewport.pxToMetres here: that converts a screen *length* to metres, which is a separate concern from the image-pixel mapping.

3 . Optional georeference — a 2-point similarity transform

Scale alone gives you metres but no true bearing — and the solar maths needs space.geo.bearing to orient the arc into the local frame (Appendix A·2). If the user can identify two points on the image whose lat/lng they know (parcel corners from a property record, two pins dropped in another map app), you can solve a similarity transform: uniform scale + rotation + translation, exactly four parameters s, theta, tx, ty. Two point correspondences give four equations — exactly enough, no least-squares needed. The recipe: project both world points to metres with the Appendix A·2 equirectangular toLocalMetres, build the image-space vector (y flipped so it points north) and the world-metres vector between the two points, then s is the length ratio and theta is the difference of their atan2 angles. The two LatLng points are exactly what BaseImage.georef = { a, b } stores.

georef.ts 
import type { Vec2, LatLng } from './model';      // model types: Section B.1
import { toLocalMetres } from './project';        // Appendix A.2: equirectangular about a ref point

export interface Similarity { s: number; theta: number; tx: number; ty: number; }

// Two correspondences: image-pixel point <-> world lat/lng. Solve s, theta, t exactly.
// Model: W = s . R(theta) . Pflip + t, where Pflip = (px.x, -px.y) flips image y to north.
export function solveSimilarity(
  aPx: Vec2, bPx: Vec2,        // same two features, in IMAGE pixels
  aLL: LatLng, bLL: LatLng,    // their known world coordinates (= BaseImage.georef.a / .b)
  ref: LatLng = aLL,           // projection reference; aLL keeps numbers small
): Similarity {
  // world points in metres (east, north) about ref
  const aW = toLocalMetres(aLL, ref);   // -> {x:east, y:north}
  const bW = toLocalMetres(bLL, ref);

  // vector between the two points in each space
  const vx = bW.x - aW.x,   vy = bW.y - aW.y;          // world metres
  const ux = bPx.x - aPx.x, uy = aPx.y - bPx.y;        // image px, y FLIPPED to point north

  const worldLen = Math.hypot(vx, vy);
  const pxLen    = Math.hypot(ux, uy);
  if (pxLen < 1) throw new Error('georef points too close in the image');
  const s = worldLen / pxLen;                          // metres per pixel (uniform scale)

  // rotation = angle(world vector) - angle(flipped image vector)
  const theta = Math.atan2(vy, vx) - Math.atan2(uy, ux);

  // translation: anchor so aPx maps onto aW.  W = s.R(theta).Pflip + t
  const c = Math.cos(theta), sn = Math.sin(theta);
  const apN = -aPx.y;                                   // flip the anchor's y too
  const tx = aW.x - s * (c * aPx.x - sn * apN);
  const ty = aW.y - s * (sn * aPx.x + c * apN);
  return { s, theta, tx, ty };
}

// Feed the engine: the similarity scale IS metresPerPixel, and theta becomes the
// rotationRad that aligns local +y onto true north. imagePxToWorld then reproduces
// the same rotation, so the trace and the georef agree pixel-for-pixel.
export function georefToCalibration(
  t: Similarity, originPx: Vec2,
): { metresPerPixel: number; rotationRad: number; originPx: Vec2 } {
  return { metresPerPixel: t.s, rotationRad: t.theta, originPx };
}
Why two points is enoughA similarity transform preserves shape — no shear, no non-uniform stretch — which is exactly right for an orthorectified top-down image: real-world rectangles stay rectangles, only scaled and rotated. Two points pin down all four degrees of freedom. If you ever had three-plus points and wanted to *average out* error, that is a least-squares affine fit — deliberately out of scope; two clean points beat three sloppy ones here. Sanity-check the solve by feeding aPx/bPx through imagePxToWorld (with the calibration from georefToCalibration): they must return aW/bW to floating-point precision. Persist geo.bearing derived from theta so the solar engine (Appendix A·2) orients correctly.

4 . Trace over the image, now in metres

With imagePxToWorld in hand (or the same function fed a calibration from georefToCalibration if georeferenced — both yield the identical local-metres frame), the B·3 boundary tool and B·4 obstacle tools need no change to their logic — only their input. Every pointer tap that previously dropped a raw Vec2 now passes through the transform first, so boundary, edges, obstacles, and overhead populate in real local metres. From there buildGridSeries and the shadow engine (shadowOf, occludersOf, sunAt, all Section B·6) work identically to the hand-measured balcony in Section B·3 — they never know an image was involved.

baseLayer-and-trace.ts 
import { makeT } from './transform';       // Section B.2: world->canvas, NORTH IS UP (y flipped)
import type { Viewport } from './transform';   // Section B.2: pan/zoom over makeT
import { imagePxToWorld, worldToImagePx } from './calibration';
import type { Space, Vec2 } from './model';

// Draw the base image UNDER the grid, in the SAME world transform as everything else.
//
// Key idea: drawImage's 9-arg form can only fill an AXIS-ALIGNED dest rect, so we do NOT
// place rotated corners by hand. Instead we build the single affine matrix mapping every
// image pixel p to its true canvas position  T(imagePxToWorld(p))  and let setTransform +
// drawImage(img, 0, 0) do the work. Rotation lives ONLY in this matrix -- never doubled
// with a separate ctx.rotate -- and the image side lengths stay w.k and h.k regardless of it.
export function drawBaseLayer(
  ctx: CanvasRenderingContext2D,
  img: HTMLImageElement,
  space: Space,
  T: ReturnType<typeof makeT>,            // from makeT(space, CW, CH) -- Section B.2
) {
  const cal = space.base!.calibration;
  const k = cal.metresPerPixel;
  const c = cal.rotationRad ? Math.cos(cal.rotationRad) : 1;
  const s = cal.rotationRad ? Math.sin(cal.rotationRad) : 0;
  const m = k * T.scale;                  // canvas px per image px, before rotation

  // Columns of the 2x2 (image px -> canvas px), derived from d/dpx of T(imagePxToWorld(p)):
  //   +1 px in image x -> world R(theta).(k,0) = (k.c, k.s) m -> canvas (m.c, -m.s)  [Y flips world y]
  //   +1 px in image y -> world R(theta).(0,-k) = (k.s, -k.c) m -> canvas (m.s,  m.c)
  const a = m * c,  b = -m * s;           // column for px.x  -> (a, b)
  const cc = m * s, d =  m * c;           // column for px.y  -> (cc, d)
  // translate so originPx (which maps to local (0,0)) lands on canvas (X(0), Y(0)):
  const e = T.X(0) - (a * cal.originPx.x + cc * cal.originPx.y);
  const f = T.Y(0) - (b * cal.originPx.x + d * cal.originPx.y);

  ctx.save();
  ctx.globalAlpha = 0.9;
  ctx.setTransform(a, b, cc, d, e, f);    // canvas = (a.x + cc.y + e, b.x + d.y + f)
  ctx.drawImage(img, 0, 0);               // natural size; the matrix scales/rotates it
  ctx.setTransform(1, 0, 0, 1, 0, 0);     // reset for the grid overlay drawn on top
  ctx.restore();
  // ...then the grid overlay draws on top at its own opacity (the Studio, Section B.7)
}

  space.boundary.push(metres);
}
Why the matrix, not corner placementA natural-looking shortcut — compute the metre position of the image's top-left and bottom-right corners and pass their deltas as drawImage width/height — silently breaks the moment the image is rotated: those corner deltas are the diagonal projections of a tilted rectangle, not its true side lengths (a 600x400 px image at 30 degrees comes out ~36 m x ~2.3 m instead of 30 m x 20 m). And re-applying ctx.rotate on top of corners that imagePxToWorld already rotated double-counts the angle. The single setTransform matrix above is the one correct placement: it agrees with T(imagePxToWorld(p)) at every pixel, rotated or not.

Analysis over time

This is the engine's home. By now the supporting pieces exist: sun(t) traces one day's simplified arc for the live animation only (Phase 02), pip and hull are the geometry primitives (Appendix A·4), and makeT owns the world-to-canvas flip at draw time (Section B·2). This section assembles the analysis pipeline that turns those into a tool: it defines the real solar position sunAt, the single Occluder shape and the occludersOf adapter, the shadow projection shadowOf, and buildGridSeries, which sweeps the seasons and emits a Grid of parallel typed arrays. Every other section (the Studio in B·7, the wiring/worker in B·8, the matcher in Phase 05) IMPORTS from here — none of them redefine these.

Two ideas drive the design. First, two suns on purpose: sun(t) is the prototype's pretty arc used only to animate the live view; sunAt(dayOfYear, hour, latRad) is the real spherical-astronomy position used for ALL analysis and sun-hours (Appendix A·2). Do not cross the streams. Second, the Grid stores cell fields as parallel Float32Arrays indexed by i = row*cols + col, not as an array of Cell objects. The logical Cell (Section B·1) is a VIEW that cellAt materializes on demand. That struct-of-arrays layout integrates fast and is zero-copy transferable to a Web Worker (Section B·8).

Southern-hemisphere season signs are baked into SEASONS, not into the declinationSolar declination δ is the same number worldwide on a given date: ≈ +23.4° around 21 June, ≈ −23.4° around 21 December. What flips between hemispheres is which date is *summer*. This app's canonical model is Southern-hemisphere (Space.geo.lat is negative). The SEASONS table below encodes that purely as a day-of-year: summer = day 355 (late December), equinox = day 80, winter = day 172 (late June). The Cooper declination formula inside sunAt then produces the correct δ sign for each day automatically — you never hand-pick ±23.4 yourself, so there is no sign to get backwards. Feed day 355 into sunAt at a negative latitude and noon altitude comes out HIGH (local summer); feed day 172 and it comes out LOW (local winter).

sunAt and sun(t): the two suns, and why three days bracket the year

You do not need 365 days of simulation. The daily arc is governed by δ, and δ is a smooth sinusoid over the year, so its extremes and midpoint — the two solstices and an equinox — bracket the whole envelope. SEASONS names exactly those three representative days. Summer (day 355) is the headline number a sun-lover needs to be high; winter (day 172) is the worst case where long shadows fall and a spot that still gets light is genuinely full-sun year-round; the equinox (day 80, sun rising due east, setting due west) samples the median. Because δ moves monotonically between them, three days approximate the year's spread to within a few percent of sun-hours at ~1% of the cost.

engine/solar.ts — SEASONS + sunAt (the analysis sun; sun(t) stays in Phase 02) 
export type Vec2 = { x: number; y: number };
export type Sun = { alt: number; altDeg: number; az: number; azDeg: number; dir: Vec2 };

// Southern-hemisphere representative days. The Cooper formula in sunAt derives the
// correct declination SIGN from the day-of-year, so there are no manual +-23.4 picks.
export const SEASONS = [
  { key: 'summer', day: 355 },
  { key: 'equinox', day: 80 },
  { key: 'winter', day: 172 },
] as const;

// The REAL solar position used for ALL analysis / sun-hours (the maths is Appendix A.2).
// dir is the ground unit vector TOWARD the sun, measured from NORTH toward EAST:
//   dir = { x: sin(az), y: cos(az) }  with E = +x, N = +y (matches the local frame).
export function sunAt(dayOfYear: number, hour: number, latRad: number): Sun {
  const d2r = Math.PI / 180;
  const decl = 23.45 * d2r * Math.sin(2 * Math.PI * (284 + dayOfYear) / 365); // Cooper
  const H = (hour - 12) * 15 * d2r;                                           // hour angle
  const alt = Math.asin(
    Math.sin(latRad) * Math.sin(decl) + Math.cos(latRad) * Math.cos(decl) * Math.cos(H),
  );
  const caz = (Math.sin(decl) - Math.sin(alt) * Math.sin(latRad)) /
              (Math.cos(alt) * Math.cos(latRad) + 1e-9);
  let az = Math.acos(Math.max(-1, Math.min(1, caz)));   // 0..PI, measured from north
  if (H > 0) az = 2 * Math.PI - az;                     // afternoon -> western half
  return { alt, altDeg: alt / d2r, az, azDeg: az / d2r, dir: { x: Math.sin(az), y: Math.cos(az) } };
}
// To respect building orientation, rotate dir by -space.geo.bearing into the local
// frame before casting shadows (one rotation, see Appendix A.2).
Keep the analysis sun honest — and where SunCalc fitssunAt is the real spherical-astronomy arc, NOT the prototype's simplified sun(t). At a Southern-hemisphere site its noon sun sits to the NORTH and the arc runs E -> N -> W. If you would rather not carry the trig, SunCalc's getPosition(date, lat, lng) (~1KB, see Appendix A.2) gives altitude/azimuth directly — but SunCalc measures azimuth from SOUTH, so convert with azFromNorth = azimuthFromSouth + Math.PI before building the same dir. Whichever you use, the rest of the pipeline is unchanged. The live animation keeps using sun(t) from Phase 02; never substitute one for the other.

One occluder shape, one adapter

shadowOf consumes exactly ONE shape — the Occluder — so the rest of the engine never branches on {foot, h, kind} variants. The single adapter occludersOf(space) turns an authored Space into that shape: each walled Edge is extruded into a thin OUTWARD quad, each Obstacle passes through as a 'vertical' occluder, and an Overhead becomes a 'overhead' slab that translates rather than hulls. shadowOf casts the footprint a distance L = h / tan(alt) opposite the sun: a vertical occluder shadows the convex hull of its base plus the projected copy; an overhead slab is translate-only (it floats, so only its outline moves). hull and pip are imported from Appendix A·4 — they are not re-derived here.

engine/occluders.ts — Occluder, shadowOf, occludersOf (hull/pip from Appendix A.4) 
import { hull } from './geom';   // Andrew monotone chain + ray-cast pip live in Appendix A.4
import type { Sun, Vec2 } from './solar';

// THE one occluder shape consumed by shadowOf.
export type Occluder = { footprint: Vec2[]; height: number; kind: 'vertical' | 'overhead'; solid?: boolean };

export function shadowOf(occ: Occluder, s: Sun, worldDiag: number): Vec2[] {
  const L = Math.min(occ.height / Math.tan(Math.max(s.alt, 0.04)), worldDiag * 2.2);
  const off = { x: -L * s.dir.x, y: -L * s.dir.y };                  // shadow falls AWAY from the sun
  const moved = occ.footprint.map(p => ({ x: p.x + off.x, y: p.y + off.y }));
  return occ.kind === 'overhead' ? moved : hull(occ.footprint.concat(moved));
}

function centroid(poly: Vec2[]): Vec2 {
  let x = 0, y = 0;
  for (let i = 0; i < poly.length; i++) { x += poly[i].x; y += poly[i].y; }
  return { x: x / poly.length, y: y / poly.length };
}

// THE one adapter: authored Space -> engine occluders. Extrudes each walled edge into
// a thin OUTWARD quad. Imported by B.7/B.8 verbatim; neither redefines it.
const WALL_THICK = 0.08;
export function occludersOf(space: any): Occluder[] {
  const out: Occluder[] = [];
  const c = centroid(space.boundary), n = space.boundary.length;
  for (let i = 0; i < n; i++) {
    const e = space.edges[i];
    if (!e || e.wall === 'none') continue;
    const a = space.boundary[i], b = space.boundary[(i + 1) % n];
    const h = e.wall === 'half' ? e.height / 2 : e.height;
    let nx = -(b.y - a.y), ny = (b.x - a.x);
    const len = Math.hypot(nx, ny) || 1; nx /= len; ny /= len;
    const mx = (a.x + b.x) / 2, my = (a.y + b.y) / 2;
    if ((mx - c.x) * nx + (my - c.y) * ny < 0) { nx = -nx; ny = -ny; }   // force OUTWARD normal
    const ox = nx * WALL_THICK, oy = ny * WALL_THICK;
    out.push({ footprint: [a, b, { x: b.x + ox, y: b.y + oy }, { x: a.x + ox, y: a.y + oy }], height: h, kind: 'vertical', solid: false });
  }
  for (let j = 0; j < space.obstacles.length; j++) {
    const o = space.obstacles[j];
    out.push({ footprint: o.footprint, height: o.height, kind: 'vertical', solid: o.solid });
  }
  if (space.overhead) out.push({ footprint: space.overhead.footprint, height: space.overhead.height, kind: 'overhead' });
  return out;
}

The integration loop: days × hours → accumulate

The core is a triple loop. The outer loop is over the three SEASONS days. Within a day we step hour from HOUR_START to HOUR_END by HOUR_STEP. At each timestep we compute sunAt, skip when the sun is below the horizon, build every occluder's shadow polygon ONCE, then mark which cells are lit. We accumulate per cell: sunHoursSummer, sunHoursWinter, and — on the summer pass — a per-hour lit array hourly that powers the Studio's chart (Section B·7). engine/grid.ts — Grid type + buildGridSeries (returns the canonical Grid; no "GridSeries") 
import { sunAt, SEASONS, type Vec2 } from './solar';
import { shadowOf, occludersOf, type Occluder } from './occluders';
import { pip } from './geom';   // ray-cast point-in-polygon, Appendix A.4
import { microclimate } from './microclimate';

export const HOUR_START = 5, HOUR_END = 20, HOUR_STEP = 0.5;
const HOURS = Math.round((HOUR_END - HOUR_START) / HOUR_STEP); // number of hourly samples

// The engine output. Parallel typed arrays, flat index i = row*cols + col.
// The logical Cell (Section B.1) is a VIEW produced by cellAt; there is no GridSeries.
export type Grid = {
  cols: number; rows: number; cellSize: number; minX: number; minY: number;
  inside: Uint8Array;                                   // 1 = usable cell
  sunHoursSummer: Float32Array; sunHoursWinter: Float32Array;
  hourly: Float32Array;                                 // SUMMER-day lit fraction; index i*HOURS + h
  hours: number[];                                      // hour-of-day for each h
  nearWall: Float32Array; wind: Float32Array; access: Float32Array;
};

export function lightClass(sunHoursSummer: number): 'full' | 'partial' | 'shade' {
  return sunHoursSummer >= 6 ? 'full' : sunHoursSummer >= 3 ? 'partial' : 'shade';
}

// cellSize default: balcony .25, garden .5, land 1.
export function buildGridSeries(space: any): Grid {
  const cellSize = space.type === 'balcony' ? 0.25 : space.type === 'garden' ? 0.5 : 1;
  const latRad = space.geo.lat * Math.PI / 180;
  const occluders = occludersOf(space);
  const solids = occluders.filter(o => o.solid);

  // 1. lay out the grid over the boundary bbox.
  const xs = space.boundary.map((p: Vec2) => p.x), ys = space.boundary.map((p: Vec2) => p.y);
  const minX = Math.min(...xs), minY = Math.min(...ys);
  const maxX = Math.max(...xs), maxY = Math.max(...ys);
  const cols = Math.ceil((maxX - minX) / cellSize), rows = Math.ceil((maxY - minY) / cellSize);
  const n = cols * rows, worldDiag = Math.hypot(maxX - minX, maxY - minY);

  const inside = new Uint8Array(n);
  const sunHoursSummer = new Float32Array(n), sunHoursWinter = new Float32Array(n);
  const hourly = new Float32Array(n * HOURS);
  const nearWall = new Float32Array(n), wind = new Float32Array(n), access = new Float32Array(n);
  const hours: number[] = [];

  const centre = (i: number): Vec2 => {
    const col = i % cols, row = (i - col) / cols;
    return { x: minX + (col + 0.5) * cellSize, y: minY + (row + 0.5) * cellSize };
  };

  // 2. mask: inside the boundary AND not under a solid occluder.
  for (let i = 0; i < n; i++) {
    const p = centre(i);
    if (!pip(p.x, p.y, space.boundary)) continue;
    if (solids.some(o => pip(p.x, p.y, o.footprint))) continue;
    inside[i] = 1;
  }

  // 3. integrate across the three representative days.
  for (const season of SEASONS) {
    let h = -1;
    for (let hour = HOUR_START; hour <= HOUR_END; hour += HOUR_STEP) {
      h++;
      if (season.key === 'summer') hours[h] = hour;     // record once
      const s = sunAt(season.day, hour, latRad);
      if (s.alt <= 0) continue;                          // sun below horizon
      const shadows = occluders.map(o => shadowOf(o, s, worldDiag));
      for (let i = 0; i < n; i++) {
        if (!inside[i]) continue;
        const p = centre(i);
        const lit = !shadows.some(sh => pip(p.x, p.y, sh));
        if (!lit) { if (season.key === 'summer') hourly[i * HOURS + h] = 0; continue; }
        if (season.key === 'summer') { sunHoursSummer[i] += HOUR_STEP; hourly[i * HOURS + h] = 1; }
        else if (season.key === 'winter') { sunHoursWinter[i] += HOUR_STEP; }
      }
    }
  }

  // 4. fill microclimate fields (B.6) for usable cells — computed, never stubbed to 0.
  for (let i = 0; i < n; i++) {
    if (!inside[i]) continue;
    const m = microclimate(centre(i), space);
    nearWall[i] = m.nearWall; wind[i] = m.wind; access[i] = m.access;
  }

  return { cols, rows, cellSize, minX, minY, inside, sunHoursSummer, sunHoursWinter, hourly, hours, nearWall, wind, access };
}

Reading cells back: cellAt and cellHourly

The UI never iterates the typed arrays directly. cellAt(g, i) materializes the logical Cell (Section B·1) on demand — reconstructing pos from the flat index, pulling the seasonal pair, deriving light via lightClass, and reading the precomputed nearWall/wind/access. cellHourly(g, i) returns the per-cell hourly series the Studio's chart consumes (Section B·7). These are the ONLY accessors; do not invent exposureSeries or other variants.

engine/grid.ts — cellAt + cellHourly (the canonical accessors) 
export function cellAt(g: Grid, i: number) {
  const col = i % g.cols, row = (i - col) / g.cols;
  return {
    pos: { x: g.minX + (col + 0.5) * g.cellSize, y: g.minY + (row + 0.5) * g.cellSize },
    sunHours: { summer: g.sunHoursSummer[i], winter: g.sunHoursWinter[i] },
    light: lightClass(g.sunHoursSummer[i]),
    nearWall: g.nearWall[i], wind: g.wind[i], access: g.access[i],
  };
}

// The chart series for cell i: one lit-fraction per hour on the summer reference day.
export function cellHourly(g: Grid, i: number): number[] {
  const H = g.hours.length, out: number[] = [];

  return out;
}

Microclimate: nearWall, wind, access (computed, not zeros)

microclimate(p, space) is the home of the three non-sun cell fields, and buildGridSeries calls it for every usable cell — they are never left at 0. nearWall rises near walled edges (shelter, thermal mass, reflected heat), wind rises near open edges (exposure), and access rises near a door position along an edge (how easy a spot is to tend and water). distanceToSegment is the hit-test helper from Section B·2.

engine/microclimate.ts — the three microclimate fields 
import { distanceToSegment } from '../viewport';   // Section B.2 hit-test helpers
import type { Vec2 } from './solar';

export function microclimate(p: Vec2, space: any) {
  let nearWall = 0, wind = 0;
  const n = space.boundary.length;
  for (let i = 0; i < n; i++) {
    const e = space.edges[i], a = space.boundary[i], b = space.boundary[(i + 1) % n];
    const infl = Math.max(0, 1 - distanceToSegment(p, a, b) / 2);
    if (e && (e.wall === 'full' || e.wall === 'half')) nearWall = Math.max(nearWall, infl);
    if (!e || e.wall === 'none') wind = Math.max(wind, infl);
  }
  let access = 0;
  for (let k = 0; k < space.edges.length; k++) {
    const e2 = space.edges[k];
    if (e2 == null || e2.door == null) continue;
    const a2 = space.boundary[k], b2 = space.boundary[(k + 1) % n];
    const d = { x: a2.x + (b2.x - a2.x) * e2.door, y: a2.y + (b2.y - a2.y) * e2.door };
    access = Math.max(access, Math.max(0, 1 - Math.hypot(p.x - d.x, p.y - d.y) / 4));
  }
  return { nearWall, wind, access };
}
Why parallel typed arrays — and how the worker transfer worksThe logical Cell/Grid model (Section B·1) is the right conceptual shape and what UI code reads through cellAt. But the heavy integration loop uses struct-of-arrays: sunHoursSummer[i], sunHoursWinter[i], hourly[i*HOURS+h]. Each is a contiguous Float32Array, so the inner loop stays monomorphic and the whole Grid is a handful of buffers you can hand to a Worker with zero-copy transfer — worker.postMessage(grid, [grid.sunHoursSummer.buffer, grid.sunHoursWinter.buffer, grid.hourly.buffer, grid.inside.buffer, grid.nearWall.buffer, grid.wind.buffer, grid.access.buffer]) (the wiring lives in Section B·8). Transferring a buffer DETACHES every view onto it on the sending side, so transfer once and treat the sender's copy as gone.
Accuracy caveats to be honest aboutThis is a 2.5-D analysis: occluders are extruded footprints with no slope, no diffuse skylight, no inter-reflection, and shadows are hard-edged (no penumbra). Three SEASONS days approximate the year but undersample the shoulder seasons — if a client needs March-vs-September asymmetry, add those day-of-year entries to SEASONS (the loop generalises; the Cooper formula handles the signs). HOUR_STEP = 0.5 gives 30-minute resolution; widen it to 1 for a fast preview or narrow it for smoother hourly curves. None of this changes the data shapes — only the fidelity.

B·7Studio

The Studio: controls + live data

The Editor (Sections B·3/B·4) produces a saved Space; buildGridSeries (Section B·6) turns it into a Grid of parallel typed arrays with integrated sunHoursSummer / sunHoursWinter, a per-cell hourly series, and the microclimate channels. The Studio is the third leg: a read-only React component that takes that Space + Grid and lets the user *see* the answer — scrub the sun across the day, watch shadows sweep, flip to the integrated sun-hours map or the seasonal Δ, and hover any cell to read its hourly exposure curve. It is the prototype in docs/sun-map-studio.html, rebuilt as a reusable component driven by a real Space instead of three baked scenes.

Everything draws on one <canvas> in painter's-order layers, plus a second, smaller canvas for the data charts so the two never fight over a redraw. No charting library, no canvas library — axes, polylines, and bars are a dozen lineTo calls each, and the data→pixel mapping is the same kind of affine transform makeT already uses for the world (Section B·2). We reuse the useAnimationFrame(onFrame, active) hook and the animate/static split from Phase 08 verbatim: in live mode the loop runs; in map and season mode it is *off* and a plain effect paints once.

What this section imports (and never redefines)

  • makeT, toWorld — the world→canvas transform and its public inverse, from Section B·2. makeT(space, CW, CH) derives its bounds straight off space.boundary; there is no world field and no synthetic world object.
  • Occluder, occludersOf, shadowOf, sunAt, sun, SEASONS, Grid, buildGridSeries, cellAt, cellHourly, lightClass — the whole engine, from Section B·6. The Studio consumes them; it does not author its own occluder shape or grid type.
  • pip, hull — point-in-polygon and convex hull, from Appendix A·4 (re-exported by the engine).
  • Space, Cell, Vec2 — the model types, from Section B·1.
  • Note the two suns are deliberate (Section B·6): sun(t) is the simplified prototype arc used for the live animation visual only; sunAt(day,hour,latRad) is the real spherical position behind every analysis number buildGridSeries bakes into the Grid. The Studio animates with sun(t) and reads pre-computed truth from the Grid.

The ordering is deliberate. Shadows go under the grid, not over it, so a lit cell painted at, say, 74% alpha still reads as gold rather than being muddied by an overlay. StudioCanvas.tsx — the component, layers, and mode-driven loop 
import { useEffect, useMemo, useRef } from 'react';
import { useAnimationFrame } from './useAnimationFrame';                 // Phase 08
import { sun, shadowOf, occludersOf, cellAt, pip } from './engine';     // Section B·6
import { makeT } from './transform';                                    // Section B·2
import { hitTestCell, indexGrid } from './hover';
import { paintGrid, drawBase, drawBoundary, drawSunGlyph, drawCompass, pathPoly } from './studioDraw';
import type { Space, Grid, Cell } from './model';                       // Section B·1

export type Mode = 'live' | 'map' | 'season';

export function StudioCanvas({
  space, grid, mode, opacity, playing, tRef, onHoverCell,
}: {
  space: Space;
  grid: Grid;                       // typed-array Grid from buildGridSeries(space) (B·6)
  mode: Mode;
  opacity: number;                  // 0..1, from the slider
  playing: boolean;
  tRef: React.MutableRefObject<number>; // time-of-day source of truth (Phase 08)
  onHoverCell: (cell: Cell | null) => void;
}) {
  const ref = useRef<HTMLCanvasElement>(null);

  // World diagonal: caps runaway shadow length when the sun is near the horizon.
  const worldDiag = useMemo(() => {
    const xs = space.boundary.map(p => p.x), ys = space.boundary.map(p => p.y);
    return Math.hypot(Math.max(...xs) - Math.min(...xs),
                      Math.max(...ys) - Math.min(...ys));
  }, [space]);

  // O(1) hover lookup, rebuilt only when the grid changes (Phase 08 useMemo rule).
  const index = useMemo(() => indexGrid(grid), [grid]);
  // Engine occluders, built once per space — Section B·6 owns occludersOf.
  const occ = useMemo(() => occludersOf(space), [space]);

  // ── DRAW: one function, layered bottom→top, called per frame OR once ──────
  const draw = (t: number) => {
    const cv = ref.current; if (!cv) return;
    const ctx = cv.getContext('2d')!;
    const dpr = Math.min(devicePixelRatio || 1, 2);
    const CW = cv.clientWidth, CH = cv.clientHeight;
    // size the backing store in device px; reset the transform to CSS px each frame
    if (cv.width !== Math.round(CW * dpr)) {
      cv.width = Math.round(CW * dpr); cv.height = Math.round(CH * dpr);
    }
    ctx.setTransform(dpr, 0, 0, dpr, 0, 0);   // 1 unit = 1 CSS px
    const T = makeT(space, CW, CH);           // world→canvas, NORTH UP (y flipped) (B·2)

    // 1 — ground + 2 — base plan
    ctx.clearRect(0, 0, CW, CH);
    drawBase(ctx, T, space);                  // base image OR vector plan; plan owned by B·4

    const s = sun(t);                          // simplified live arc: { altDeg, alt, azDeg, dir }
    const shadows = occ.map(o => shadowOf(o, s, worldDiag)); // engine Occluder -> hull/translate

    if (mode === 'live' && s.altDeg > 2) {
      // 3 — moving cast shadows (translucent, UNDER the grid)
      ctx.save();
      ctx.fillStyle = 'rgba(20,22,30,0.30)';
      for (const sh of shadows) { pathPoly(ctx, T, sh); ctx.fill(); }
      ctx.restore();
    }

    // 4 — grid cells, the ONLY opacity-bound layer
    ctx.globalAlpha = opacity;
    paintGrid(ctx, T, grid, mode, s, shadows);
    ctx.globalAlpha = 1;

    // 5 — boundary + structures, 6 — sun glyph + compass (screen space)
    drawBoundary(ctx, T, space);
    if (mode === 'live' && s.altDeg > 1) drawSunGlyph(ctx, CW, CH, T, s);
    drawCompass(ctx, CW, s);
  };

  // STATIC: map & season modes paint exactly once per input change — loop OFF
  useEffect(() => { if (mode !== 'live') draw(tRef.current); },
    // eslint-disable-next-line react-hooks/exhaustive-deps
    [mode, opacity, space, grid]);

  // ANIMATE: the loop only exists while live AND playing (Phase 08 contract).
  // dt is delta SECONDS from the hook; 12 real seconds = one simulated day.
  useAnimationFrame((dt: number) => {
    tRef.current = (tRef.current + dt / 12) % 1;
    draw(tRef.current);
  }, mode === 'live' && playing);

  // Scrub / pause repaint while the loop is off: redraw when t changes externally.
  useEffect(() => { if (mode === 'live' && !playing) draw(tRef.current); });

  return (
    <canvas
      ref={ref}
      onPointerMove={(e) => onHoverCell(hitTestCell(e, ref.current!, space, grid, index))}
      onPointerLeave={() => onHoverCell(null)}
    />
  );
}
Why opacity wraps only the gridctx.globalAlpha is *stateful* on the context — anything drawn while it is set inherits it. Set it right before paintGrid and reset to 1 immediately after, so the boundary line and sun glyph stay crisp. If you set it earlier (around the shadows) the moving shade also fades and the live view loses its punch. Always pair the set with the reset; a forgotten reset silently ghosts every later layer. (Same discipline applies to setTransform: re-establish dpr scaling at the top of every draw, because the backing-store resize above resets the canvas state.)

import { pip, cellAt, lightClass } from './engine';   // Section B·6
import { makeT } from './transform';                  // Section B·2
import type { Space, Grid } from './model';
import type { Mode } from './StudioCanvas';

type T = ReturnType<typeof makeT>;   // { scale, X, Y, S, cx, cy } — the B·2 shape
type Sun = ReturnType<typeof import('./engine').sun>;
type Vec2 = { x: number; y: number };

export function pathPoly(ctx: CanvasRenderingContext2D, T: T, poly: Vec2[]) {
  ctx.beginPath();
  poly.forEach((p, i) => i ? ctx.lineTo(T.X(p.x), T.Y(p.y)) : ctx.moveTo(T.X(p.x), T.Y(p.y)));
  ctx.closePath();
}

// suitability ramp: cool shade → warm full sun (same stops as the prototype)
const RAMP = ['#3A4D72', '#6E86B8', '#C6A45E', '#F2B84B'];
const hx = (h: string) => [1, 3, 5].map(i => parseInt(h.slice(i, i + 2), 16));
const mix = (a: string, b: string, f: number) => {
  const A = hx(a), B = hx(b);
  return `rgb(${A.map((c, i) => Math.round(c + (B[i] - c) * f)).join(',')})`;
};
function ramp(f: number) {
  f = Math.max(0, Math.min(1, f));
  const seg = f * (RAMP.length - 1);
  const i = Math.min(Math.floor(seg), RAMP.length - 2);
  return mix(RAMP[i], RAMP[i + 1], seg - i);
}

// Paint every IN cell. `mode` decides the colour; `globalAlpha` is set by the caller.
// The Grid (B·6) is parallel typed arrays; iterate flat indices and use cellAt to
// materialise the logical Cell only when we need its pos for the live shadow test.
export function paintGrid(
  ctx: CanvasRenderingContext2D, T: T, grid: Grid, mode: Mode, s: Sun, shadows: Vec2[][],
) {
  const half = grid.cellSize / 2, cs = grid.cellSize;
  // normalising maxima for the two static maps (only over IN cells)
  let maxSun = 0.0001, maxDelta = 0.0001;
  for (let i = 0; i < grid.inside.length; i++) {
    if (!grid.inside[i]) continue;
    if (grid.sunHoursSummer[i] > maxSun) maxSun = grid.sunHoursSummer[i];
    const d = grid.sunHoursSummer[i] - grid.sunHoursWinter[i];
    if (d > maxDelta) maxDelta = d;
  }
  for (let i = 0; i < grid.inside.length; i++) {
    if (!grid.inside[i]) continue;
    const col = i % grid.cols, row = (i - col) / grid.cols;
    const cx = grid.minX + (col + 0.5) * cs, cy = grid.minY + (row + 0.5) * cs;
    let fill: string;
    if (mode === 'live') {
      // instantaneous: is this cell inside any cast shadow right now?
      const lit = s.altDeg > 2 && !shadows.some(sh => pip(cx, cy, sh));
      fill = lit ? '#F2B84B' : '#2C3550';
    } else if (mode === 'map') {
      fill = ramp(grid.sunHoursSummer[i] / maxSun);                 // integrated sun-hours
    } else { // season: summer − winter Δ-hours, straight off the baked typed arrays
      fill = ramp((grid.sunHoursSummer[i] - grid.sunHoursWinter[i]) / maxDelta);
    }
    ctx.fillStyle = fill;
    // +0.6 px overdraw closes seams between cells; T.Y(top) since y is flipped
    ctx.fillRect(T.X(cx - half), T.Y(cy + half), T.S(cs) + 0.6, T.S(cs) + 0.6);
  }
}

export function drawBase(ctx: CanvasRenderingContext2D, T: T, space: Space) {
  // 1 — flat ground backdrop (whole canvas)
  ctx.fillStyle = '#1B1A16';
  ctx.fillRect(0, 0, ctx.canvas.clientWidth, ctx.canvas.clientHeight);
  // 2 — authored base image, placed via its calibration (metresPerPixel + originPx).
  // The image→world placement uses imagePxToWorld(...) from Section B·5; the optional
  // large-image IndexedDB path (loadBaseFromIDB) must be awaited before this paints (B·1).
  // The vector-plan fallback (substrate/beds/obstacles) lives in the Editor's drawPlan (B·4).
  // base bitmaps are pre-decoded into an HTMLImageElement cache keyed by space.base.dataUrl.
}

export function drawBoundary(ctx: CanvasRenderingContext2D, T: T, space: Space) {
  pathPoly(ctx, T, space.boundary);
  ctx.strokeStyle = '#A89F8C'; ctx.lineWidth = 1.5; ctx.stroke();
  ctx.fillStyle = '#E9A23A';
  for (const p of space.boundary) {
    ctx.beginPath(); ctx.arc(T.X(p.x), T.Y(p.y), 2.6, 0, Math.PI * 2); ctx.fill();
  }
}

// Sun glyph: orbits the WORLD-rect centre in SCREEN space. dir is the ground
// unit vector toward the sun (E=+x, N=+y); screen y is down, so negate dir.y.
export function drawSunGlyph(ctx: CanvasRenderingContext2D, CW: number, CH: number, T: T, s: Sun) {
  const r = Math.min(CW, CH) * 0.46;
  const px = T.cx + s.dir.x * r, py = T.cy - s.dir.y * r;
  const g = ctx.createRadialGradient(px, py, 0, px, py, 38);
  g.addColorStop(0, 'rgba(233,162,58,0.9)'); g.addColorStop(1, 'rgba(233,162,58,0)');
  ctx.fillStyle = g; ctx.beginPath(); ctx.arc(px, py, 38, 0, Math.PI * 2); ctx.fill();
  ctx.fillStyle = '#E9A23A'; ctx.beginPath(); ctx.arc(px, py, 8, 0, Math.PI * 2); ctx.fill();
}

// Compass rose: fixed top-right, north up. azDeg is clockwise from north;
// screen angle measured from +x (east) is (azDeg − 90)°.
export function drawCompass(ctx: CanvasRenderingContext2D, CW: number, s: Sun) {
  const cx = CW - 34, cy = 34, r = 18;
  ctx.fillStyle = 'rgba(15,13,9,0.7)';
  ctx.beginPath(); ctx.arc(cx, cy, r + 8, 0, Math.PI * 2); ctx.fill();
  ctx.strokeStyle = 'rgba(168,159,140,0.4)'; ctx.lineWidth = 1;
  ctx.beginPath(); ctx.arc(cx, cy, r, 0, Math.PI * 2); ctx.stroke();
  ctx.font = '600 9px ui-monospace, Menlo, monospace';
  ctx.fillStyle = '#A89F8C'; ctx.textAlign = 'center'; ctx.textBaseline = 'middle';
  ctx.fillText('N', cx, cy - r); ctx.fillText('S', cx, cy + r);
  ctx.fillText('E', cx + r, cy); ctx.fillText('W', cx - r, cy);
  if (s.altDeg > 1) {
    const a = (s.azDeg - 90) * Math.PI / 180;
    ctx.fillStyle = '#E9A23A';
    ctx.beginPath(); ctx.arc(cx + Math.cos(a) * r, cy + Math.sin(a) * r, 3.4, 0, Math.PI * 2); ctx.fill();
  }
  ctx.textAlign = 'start';
}

Controls — plain React state, one boolean per loop

The controls are ordinary React state lifted into the parent Studio: a space selector (<select> over saved spaces), play/pause (toggles playing), a time scrubber (<input type=range> writing tRef.current), a mode toggle (live | map | season), and the grid-opacity slider. The crucial wiring is that *mode* gates the animation loop: when mode is not live, useAnimationFrame's active argument is false, so per the Phase 08 hook there is literally no requestAnimationFrame running — the static effect paints once and the CPU goes idle.

Drawing data on canvas — the coordinate mapping

A chart is just a second affine transform: data space → pixel space, exactly like makeT maps world → canvas (Section B·2). Pick a plot rectangle r = {x, y, w, h} inside the panel canvas (leave margins for axis labels). A value v in [lo, hi] maps to a pixel with f = (v − lo)/(hi − lo); along X it is r.x + f·r.w, and along Y it is r.y + r.h − f·r.h — the subtraction flips Y so larger values sit higher, the same flip makeT does for north. Ticks are evenly spaced data values run back through that same formula. Get the mapping right once and both the line chart and the histogram fall out of it.

charts.ts — axes, line chart, histogram (no library) 
export type Rect = { x: number; y: number; w: number; h: number };

// Map a data value in [lo,hi] to a pixel along an axis of length `len` from `base`;
// `up=true` flips Y so larger values sit higher (the north-up flip, for data).
const toPx = (v: number, lo: number, hi: number, base: number, len: number, up = false) => {
  const f = hi === lo ? 0 : (v - lo) / (hi - lo);
  return up ? base + len - f * len : base + f * len;
};

function drawAxes(
  ctx: CanvasRenderingContext2D, r: Rect,
  xTicks: { at: number; label: string }[],   // at ∈ [0,1] across width
  yMax: number, yUnit: string,
) {
  ctx.lineWidth = 1;
  ctx.font = '10px ui-monospace, Menlo, monospace';
  // L-shaped axes
  ctx.strokeStyle = '#3A352A';
  ctx.beginPath();
  ctx.moveTo(r.x, r.y); ctx.lineTo(r.x, r.y + r.h); ctx.lineTo(r.x + r.w, r.y + r.h);
  ctx.stroke();
  // y ticks + gridlines: 0 .. yMax in 4 steps
  ctx.fillStyle = '#A89F8C'; ctx.textAlign = 'right'; ctx.textBaseline = 'middle';
  for (let i = 0; i <= 4; i++) {
    const v = (yMax * i) / 4;
    const py = toPx(v, 0, yMax, r.y, r.h, true);
    ctx.fillText(v.toFixed(1), r.x - 6, py);
    ctx.strokeStyle = 'rgba(58,53,42,0.6)';
    ctx.beginPath(); ctx.moveTo(r.x, py); ctx.lineTo(r.x + r.w, py); ctx.stroke();
  }
  ctx.fillStyle = '#A89F8C'; ctx.fillText(yUnit, r.x - 6, r.y - 8);
  // x ticks
  ctx.textAlign = 'center'; ctx.textBaseline = 'top';
  for (const t of xTicks) ctx.fillText(t.label, r.x + t.at * r.w, r.y + r.h + 5);
}

// LINE CHART — one cell's per-hour summer lit-fraction across the day.
// `series` is cellHourly(grid, i) from Section B·6; the Studio does NOT recompute it.
export function drawLineChart(
  ctx: CanvasRenderingContext2D, series: number[], rect: Rect,
) {
  const r: Rect = { x: rect.x + 34, y: rect.y + 10, w: rect.w - 44, h: rect.h - 34 };
  const yMax = 1;                              // lit fraction is already normalised 0..1
  const n = series.length;
  drawAxes(ctx, r, [
    { at: 0, label: '6h' }, { at: 0.5, label: '12h' }, { at: 1, label: '18h' },
  ], yMax, 'lit');
  if (n === 0) return;
  // polyline
  ctx.strokeStyle = '#E9A23A'; ctx.lineWidth = 2; ctx.lineJoin = 'round';
  ctx.beginPath();
  series.forEach((v, i) => {
    const px = r.x + (n === 1 ? 0 : (i / (n - 1)) * r.w);
    const py = toPx(v, 0, yMax, r.y, r.h, true);
    i ? ctx.lineTo(px, py) : ctx.moveTo(px, py);
  });
  ctx.stroke();

Hover-to-inspect: pointer → cell index → baked series

The Grid (Section B·6) is a regular lattice anchored at grid.minX/grid.minY with a flat index i = row*cols + col, so the lookup is O(1) index arithmetic, not a scan. Invert makeT to get world coords from the pointer, snap to the nearest column/row, compute the flat index, and check grid.inside[i] to reject the holes (cells outside the boundary or inside a solid occluder). If it is in, materialise the logical Cell with cellAt(grid, i) and read its hourly curve with cellHourly(grid, i) — no recomputation in the Studio, the analysis was baked once by buildGridSeries.

Inverting makeT needs no private fields: use the public inverse toWorld(T, sx, sy) from Section B·2, which is defined purely in terms of T.X(0), T.Y(0) and T.scale. Feed it the pointer position relative to the canvas and you get back world metres directly; the north-up Y flip is already handled inside toWorld.

export function hitTestCell(
  e: { clientX: number; clientY: number },
  canvas: HTMLCanvasElement,
  space: Space,
  grid: Grid,
  _index: Grid,
): Cell | null {
  const rect = canvas.getBoundingClientRect();   // CSS px — matches makeT input (B·2)
  const T = makeT(space, rect.width, rect.height);
  const sx = e.clientX - rect.left, sy = e.clientY - rect.top;
  const w = toWorld(T, sx, sy);                  // world metres; Y flip handled in toWorld

  const col = colOf(w.x, grid), row = rowOf(w.y, grid);
  if (col < 0 || col >= grid.cols || row < 0 || row >= grid.rows) return null;
  const i = row * grid.cols + col;
  if (!grid.inside[i]) return null;              // skip holes (outside boundary / solid)
  return cellAt(grid, i);                        // materialise the logical Cell (B·6)
}

// Find the flat index of a Cell so the panel can read its baked hourly series.
export function indexOfCell(cell: Cell, grid: Grid): number {
  const col = colOf(cell.pos.x, grid), row = rowOf(cell.pos.y, grid);
  return row * grid.cols + col;

Wiring, performance & correctness

Everything from Phase 00 onward now exists as parts: a Space model with its SpaceStore (Section B·1), the world transform makeT/toWorld/Viewport (Section B·2), the Editor that authors a Space (Sections B·3-B·5), the engine that integrates sun-hours (buildGridSeries, occludersOf, sunAt, SEASONS — Section B·6), and the Studio that visualizes it (Section B·7). This section is the glue. We route between the gallery, the Editor and the Studio with the react-router that's already in the project, and replace the old onboarding step 2 (see Phase 07) with the real flow. Then we make it fast: buildGridSeries is the one genuinely heavy computation, so it runs off-thread in a plain module Web Worker, returning the canonical Grid of transferable typed arrays so a multi-season orbit over a few hundred cells never blocks a pointer drag. Finally we make it trustworthy — a headless Node test that pins the engine's output ranges, and an honest accounting of where the simplified physics stops being accurate.

No new dependencies. The worker is a vanilla ES module, the transferables are the Float32Arrays already inside Grid, and the test runs under the Node test runner that ships with Node itself. The only library named anywhere remains SunCalc — still optional, still an aside (see Appendix A2).

No new engine signatures — analysis uses sunAt + SEASONSThe seasonal integral fills Cell.sunHours.{summer,winter} from the real spherical sun, sunAt(dayOfYear, hour, latRad), swept over the SEASONS table — both defined in Section B·6. Performance: buildGridSeries in a Web Worker

buildGridSeries (Section B·6) integrates sun-hours by stepping sunAt across the day (HOUR_START..HOUR_END step HOUR_STEP — ~30 samples) and, at each step, projecting every occluder's shadow via shadowOf(occludersOf(space)[k], s, worldDiag) and testing every cell with pip. That's samples × occluders × cells shadow-builds and point-in-polygons, repeated for each entry in SEASONS. For a balcony it's instant; for the land scene with a fine grid it's tens of milliseconds — enough to drop a frame mid-drag. So we hand the whole call to a worker. The main thread posts the Space plus grid params and gets back the Grid's transferable Float32Arrays; it never runs the integral itself.

The protocol is deliberately flat — structured-clone the Space (it is plain JSON-shaped data, so clone is cheap and lossless), run buildGridSeries inside the worker, and transfer back the Grid's typed arrays (inside, sunHoursSummer, sunHoursWinter, hourly, nearWall, wind, access) by reference instead of copying. The Grid is already a struct-of-parallel-arrays (B·6) precisely so it is worker-transferable — there is no array-of-Cell to repack. The logical Cell is materialized on demand on the main thread with cellAt(grid, i).

import type { Space, Grid } from './model';
import { buildGridSeries } from './engine'; // B·6 — the SAME function the test uses

export type GridRequest = {
  reqId: number;
  space: Space;
  cellSize: number;     // balcony .25, garden .5, land 1 (caller picks per type)
};
// The reply IS the canonical Grid plus a reqId for last-write-wins matching.
export type GridReply = Grid & { reqId: number };

self.onmessage = (e: MessageEvent<GridRequest>) => {
  const { reqId, space, cellSize } = e.data;
  // Build the full Grid off-thread: rasterise space.boundary, sweep sunAt over
  // every SEASON, fill sunHours.{summer,winter}, the SUMMER `hourly` series, and
  // nearWall/wind/access via microclimate(center, space). All inside B·6.
  const g: Grid = buildGridSeries(space, cellSize);
  const reply: GridReply = { reqId, ...g };
  // Transfer the underlying ArrayBuffers — zero-copy handoff. Each typed array
  // owns a distinct buffer, so there is no double-transfer.
  (self as unknown as Worker).postMessage(reply, [
    g.inside.buffer,
    g.sunHoursSummer.buffer, g.sunHoursWinter.buffer,
    g.hourly.buffer,
    g.nearWall.buffer, g.wind.buffer, g.access.buffer,
  ]);
};

useGridWorker.ts — main-thread caller; returns the canonical Grid 
import { useEffect, useRef, useState } from 'react';
import type { Space, Grid } from './model';
import type { GridRequest, GridReply } from './grid.worker';

// Vite resolves this URL form to a bundled module worker — no plugin, no lib.
function spawn(): Worker {
  return new Worker(new URL('./grid.worker.ts', import.meta.url), { type: 'module' });
}

export function useGridWorker(space: Space | null, cellSize: number) {
  const [grid, setGrid] = useState<Grid | null>(null);
  const [pending, setPending] = useState(false);
  const workerRef = useRef<Worker | null>(null);
  const reqIdRef = useRef(0);

  useEffect(() => {
    const w = spawn();
    workerRef.current = w;
    w.onmessage = (e: MessageEvent<GridReply>) => {
      // Ignore stale replies from a superseded Space (last-write-wins).
      if (e.data.reqId !== reqIdRef.current) return;
      const { reqId, ...g } = e.data;   // strip reqId -> a clean canonical Grid
      setGrid(g as Grid);
      setPending(false);
    };
    return () => w.terminate(); // StrictMode double-mount safe: terminate on cleanup
  }, []);

  useEffect(() => {
    const w = workerRef.current;
    if (!w || !space) { setGrid(null); return; }
    const reqId = ++reqIdRef.current;
    setGrid(null);      // clear stale grid so the Studio shows its pending state
    setPending(true);
    const msg: GridRequest = { reqId, space, cellSize };
    w.postMessage(msg); // Space is structured-cloned (plain data -> cheap)
  }, [space, cellSize]);

  return { grid, pending };
}

Correctness: a headless engine test (no browser)

Analysis uses sunAt — real declination (Cooper) + hour angle (see Appendix A2) — but still ignores the analemma, atmospheric refraction near the horizon, and the equation of time (solar vs clock minutes). The live overlay's sun(t) is cruder still, sinusoidal by design; it is visual only and never feeds sun-hours. For survey-grade altitude/azimuth, swap sunAt for SunCalc (~1KB, optional — Appendix A2); the rest of the pipeline is unchanged because both produce { alt, az, dir }. (2) 2.5-D shadows. shadowOf (B·6) projects flat footprints at one height (L = h/tan(alt), clamped at low sun and capped at worldDiag*2.2); it has no notion of sloped roofs, gaps under canopies, or partial transmission through foliage — a tree is opaque, and an overhead slab is a translate-only shadow. (3) Flat-earth projection. Local metres assume a tangent plane; over a small land plot the error is sub-metre, but georeferenced imagery (BaseImage.georef) spanning hundreds of metres accrues real projection error, and non-orthorectified photos (a phone shot at an angle) distort metresPerPixel across the frame (see Section B·5). Surface these as confidence, not certainty. (4) A11y + reduced motion. B·9Storage

Storing it: polygons of any shape

When you outgrow localStorage (Section B·1) and move spaces to a real database, one question trips everyone up: how do you store a shape that might be a rectangle, an L, or a balcony wrapped around a curved building? The trap is reaching for a matrix. The way out is to notice you are storing two different things, and they want opposite shapes:

two things, stored two ways 
  AUTHORED — the source of truth          DERIVED — computed from the truth
  (persist this)                          (recompute on load; cache only if slow)

  Space {                                 Grid {
    boundary : Vec2[]   ──build──▶          inside    : Uint8Array
    edges, obstacles                        sunHours  : Float32Array
    overhead, geo                           index = row*cols + col
  }                                       }
     │                                       │
     ▼  store as JSON / jsonb / GeoJSON      ▼  don't store — or pack as blobs
   one ordered list of points              a rectangular array + a mask

The shape is not a grid, and the grid is not the shape. Store the outline as a list of points; store the weights, if at all, as a flat array. Conflating them is what makes circular balconies feel hard.

One shape of data for every outline

Your boundary is already the right representation: an ordered list of vertices. A rectangle is four points, an L-shape is six, and a curved balcony is just more points sampled along the arc. There is no “rectangular vs curved” storage distinction — a curve is not a special case, it is simply more vertices. A matrix is the wrong model for an outline: it cannot place a vertex precisely, and it forces a raster before you have stored anything.

the same data shape, whatever the outline 
  RECTANGLE — 4 pts        L-SHAPE — 6 pts          CIRCULAR BALCONY — ~16 pts
   o---------o             o-------o                      o o o
   |         |             |       |                  o         o
   |         |             |       o-----o          o             o
   |         |             |             |            o          o
   o---------o             o-------------o               o o o o
  [a, b, c, d]            [ ...6 points ]            [ ...16 points ]

        every case is the SAME shape of data: an ordered list of points.
        sample a curve into vertices once, at author time, and move on.
the outline, two interchangeable encodings 
// Vec2[] — the app's native form, in local metres (the engine speaks this)
"boundary": [{ "x": 0, "y": 0 }, { "x": 4, "y": 0 }, { "x": 4, "y": 2.5 }, { "x": 0, "y": 2.5 }]

// GeoJSON Polygon — the interop form. coordinates is an array of RINGS:
// ring[0] = outer boundary, ring[1..] = holes, each ring closed (first == last).
{ "type": "Polygon",
  "coordinates": [
    [ [0,0], [4,0], [4,2.5], [0,2.5], [0,0] ]
  ] }

Putting a polygon in a database

For a per-user app the simplest store wins: keep the whole geometry as one JSON value. Reach for heavier machinery only when you actually need spatial queries.

spaces — the source of truth as a single jsonb document 
-- one row per saved space; the geometry travels as a unit
CREATE TABLE spaces (
  id             uuid PRIMARY KEY,
  name           text NOT NULL,
  type           text NOT NULL,            -- 'balcony' | 'garden' | 'land'
  geometry       jsonb NOT NULL,           -- { boundary, edges, obstacles, overhead, geo }
  base           jsonb,                     -- { dataUrl | blobRef, calibration }
  schema_version int NOT NULL DEFAULT 1,
  created_at     timestamptz NOT NULL DEFAULT now()
);
  • Plain JSON / jsonb (recommended) — DB-agnostic, portable, read and written as one unit. This is your B·1 SpaceStore, lifted to a server. Do not normalise vertices into a one-row-per-point table — it is slower and buys nothing; a boundary is always read and written whole.
  • GeoJSON — pick it when you want a standard or need holes (its rings give you a pond inside a garden for free).
  • PostGIS geometry(Polygon) + a GiST index — only when you need server-side spatial queries (ST_Contains, ST_Area, proximity). For one user's saved spaces this is overkill.

Two habits keep the data honest: store vertices in your local-metre frame (not raw lat/lng — keep the shadow maths clean and put a geo: { lat, lng, bearing } georeference beside it, per Section B·5), and keep a consistent winding (outer ring counter-clockwise) so the shoelace area sign (Section B·3) and point-in-polygon (Appendix A·4) stay robust.

Don't model arcs as a primitive It is tempting to store a circle as { center, radius } or edges as line/arc segments. Resist it for v1: polygon approximation is universal, every consumer (drawing, hit-testing, pip, shadowOf) already speaks polygons, and the analysis rasterises to a grid anyway — sub-cell curve precision is discarded the moment you build the Grid. Sample the arc into vertices at author time; you lose nothing visible and you keep one code path.

The weights are a grid — a square box plus an “inside” mask

Here is where the circular-balcony worry actually dissolves. The per-cell weights live in a grid, and that grid is always a rectangle over the bounding box — the shape does not live in the grid's outline, it lives in an inside mask. A square array can hold any shape because the polygon decides which cells are usable; the corners a circle leaves empty are simply marked inside = 0 and ignored. That is exactly the Grid.inside: Uint8Array from Section B·6.

a non-rectangular outline in a perfectly rectangular array 
  the polygon (vertices)         rasterised into a SQUARE grid + inside mask
      _____                       col→  0 1 2 3 4 5 6
     /     \                      row0  0 0 1 1 1 0 0     0 = outside  (ignored)
    /       \                     row1  0 1 1 1 1 1 0     1 = usable   (carries weight)
   |         |   ──rasterise──▶   row2  1 1 1 1 1 1 1
   |         |                    row3  1 1 1 1 1 1 1     weight is stored ONLY
    \       /                     row4  0 1 1 1 1 1 0     where inside = 1
     \_____/                      row5  0 0 1 1 1 0 0

  stored as: boundary: Vec2[]     stored as: { cols, rows, cellSize, minX, minY }
             (the TRUTH)                      + flat arrays, index = row*cols + col

So you get the easy rectangular array you imagined and arbitrary shapes: rasterise the vertex list into the mask once, and out-of-boundary cells carry inside = 0. A sparse form (only inside cells as { col, row, weight }) is a niche win for a thin sliver in a huge box, but it loses O(1) index = row*cols + col access — prefer dense + mask.

Recompute the grid; cache only if you must

The strongest advice: don't persist the grid at all. It is a pure function of (boundary + structures + latitude + sun model), and buildGridSeries(space) (Section B·6) runs in milliseconds. Storing it invites staleness — move one wall and a saved grid is silently wrong. If recompute is genuinely too slow (large land, server-side analytics, offline), cache it as flat byte blobs plus an invalidation hash:

grid_cache — derived, packed flat, invalidated by an inputs hash 
CREATE TABLE grid_cache (
  space_id     uuid PRIMARY KEY REFERENCES spaces(id) ON DELETE CASCADE,
  cols int, rows int, cell_size real, min_x real, min_y real,
  inside       bytea,   -- packed Uint8Array,  index = row*cols + col
  sun_summer   bytea,   -- packed Float32Array
  sun_winter   bytea,
  inputs_hash  text,    -- hash(geometry); cache is stale when it stops matching
  computed_at  timestamptz DEFAULT now()
);
pack a typed array for a text store (or write a.buffer straight to BYTEA) 
// small grids: base64 into JSON. BIG grids: store the raw a.buffer bytes in
// BYTEA instead — fromCharCode(...) spreads every byte and will blow the
// call stack past ~100k elements.
export function packF32(a: Float32Array): string {
  return btoa(String.fromCharCode(...new Uint8Array(a.buffer)));
}
export function unpackF32(b64: string): Float32Array {
  const bin = atob(b64);
  const bytes = new Uint8Array(bin.length);
  for (let i = 0; i < bin.length; i++) bytes[i] = bin.charCodeAt(i);
  return new Float32Array(bytes.buffer);
}

The inputs_hash is the whole trick: hash the stored geometry when you compute the grid; on load, recompute the hash and treat the cache as a miss if it differs. The cache can never silently disagree with the shape it came from.

Where holes go You rarely need a true polygon hole. An interior pillar, a pond, a raised bed — these are obstacles (Section B·1) with solid: true, which already punch holes in the usable area by excluding those cells from the mask. Reach for GeoJSON inner rings only when a hole must change the boundary outline itself.

Appendix · the maths, from scratch
Every clever thing here is one of four small ideas.

You said you wanted to learn the arithmetic, not just paste it. Good — because under the whole engine there are only four moving parts: a little trigonometry, the sun's geometry, a timing loop, and one polygon test. Here's each one derived, the line of code it became, and where to read further.

A·1Trig

Trigonometry — just the three you actually need

Radians, because the computer insists

Math.sin, cos, and tan all expect radians, not degrees. A full circle is 2π radians = 360°, so half a circle (a straight line) is π = 180°. That's why every angle in the code gets multiplied by Math.PI/180 on the way in. Forgetting this is the single most common bug in this kind of code — your sun will appear to teleport because Math.sin(90) means 90 radians (≈ 14 full turns), not 90°.

The unit circle is the whole mental model

Picture a point travelling around a circle of radius 1. At angle θ its coordinates are exactly (cos θ, sin θ). Cosine is the horizontal part, sine is the vertical part. That single fact is most of what we use.

the unit circle 
            90° (0, 1)
               |   • ← point at angle θ
               |  /|        is (cos θ, sin θ)
               | / | sin θ  ← height
       180° ---+---+--- 0°  (1, 0)
       (-1,0)  |  cos θ
               |   width
            270° (0, -1)

Why sin(π·t) draws an entire day of sun

As t runs from 0 to 1, the expression π·t runs from 0 to π, and the sine of that traces a smooth hump: 0 → 1 → 0. Multiply by the peak altitude and you have the sun rising from the horizon, reaching its highest point at midday (t = 0.5), and setting again — in one line.

altitude across the day — the shape of sin(π·t) 
altitude
  74° ┤            ___
      │         _-     -_
      │       /           \        altDeg = 74 * Math.sin(Math.PI * t)
      │     /               \
   0° ┼───/───────┼───────────\───
      t=0       t=0.5        t=1
   sunrise      noon        sunset

Turning a compass bearing into a direction

The sun's ground direction is (sin A, cos A). If that looks like sine and cosine are swapped from the unit circle above — they are, on purpose. I measure the bearing clockwise from north, and I want north to point "up" as (0, 1). So north (0°) → (0, 1), east (90°) → (1, 0): the east-west component is sin(bearing) and the north-south component is cos(bearing). Pick a convention once, write it down, and stick to it — half of all geometry bugs are a mismatched convention.

tan and the length of a shadow — one triangle

This is the keystone. Stand a wall of height h in sunlight. The sun sits at altitude α above the horizon. The ray grazing the top of the wall continues down to the ground, and the wall, the ground, and that ray form a right triangle:

shadow geometry — similar triangles 
 sun ray ↘
          ↘
        +----•  top of wall
        |    |↘
   h →  |    |  ↘            tan(α) = opposite / adjacent = h / L
        |    | α  ↘
        +----+------•---  ground       ⇒   L = h / tan(α)
          wall    L = shadow

tan(α) = opposite / adjacent = h / L, so L = h / tan(α). Now feel the behaviour: a 3 m wall at midday (α ≈ 74°) casts 3 / tan(74°) = 3 / 3.49 ≈ 0.86 m — a stubby shadow. The same wall at dusk (α ≈ 15°) casts 3 / tan(15°) = 3 / 0.27 ≈ 11 m — a long one. The entire "shadows stretch at dawn and dusk" effect is that one division.

A·2Sun

The solar position algorithm

The studio uses a deliberately clean parametric arc: sin(π·t) for height and a linear east → north → west sweep. That's honest enough to teach with, but the real position of the sun for a given date, time, and latitude comes from spherical astronomy. Here are the standard equations — the ones every library implements — with each symbol in plain words.

Three angles describe where the sun is

  • Declination δ — the sun's seasonal tilt. It swings between +23.45° (June) and −23.45° (December) as Earth orbits. This is why winter sun is low and summer sun is high.
  • Hour angle H — how far the sun is from solar noon. Earth turns 360° in 24 h, so 15° per hour: morning is negative, afternoon positive.
  • Latitude φ — where you are, straight from the lat/long you captured in phase 02.
declination & hour angle (degrees) 
// N = day of the year, 1–365.  Cooper's 1969 approximation.
const decl = 23.45 * Math.sin(rad(360 * (284 + N) / 365))
// e.g. N = 355 (21 Dec) → decl ≈ −23.4°  (southern summer; sun over the Tropic of Capricorn)

const H = 15 * (solarHour - 12)   // −45° at 9am, 0° at noon, +30° at 2pm

Combine them into altitude and azimuth

With φ, δ, and H you get the two numbers the engine actually wants — how high the sun is (altitude) and which compass direction it's in (azimuth):

the spherical-astronomy core (radians) 
// altitude: 0° at the horizon, 90° straight overhead
const alt = Math.asin( sin(φ)*sin(δ) + cos(φ)*cos(δ)*cos(H) )

// azimuth, measured clockwise from north
let az = Math.acos( (sin(δ) - sin(alt)*sin(φ)) / (cos(alt)*cos(φ)) )
if (H > 0) az = 2*Math.PI - az            // afternoon: mirror to the western half
Two traps Convention: some textbooks measure azimuth from south, not north — always sanity-check against a known sunrise direction. The zenith: when the sun is nearly overhead (the tropics at noon), cos(alt) ≈ 0 and azimuth becomes numerically unstable. That's exactly why the robust libraries use an atan2 form instead of acos.

Solar time is not clock time

Two corrections turn your wall clock into solar time: your longitude's offset inside its timezone, and the Equation of Time — because Earth's orbit is an ellipse, the sun runs up to ±16 minutes fast or slow over the year. Libraries fold both in; if you roll your own, this is the part that quietly makes everything 10 minutes wrong.

Reach for a library to ship Use the formulas above to understand; use SunCalc (≈ 1 KB) to ship — SunCalc.getPosition(date, lat, lng) hands back altitude and azimuth, corrections and all. The maths is here so the library is never a black box to you.

A·3Motion

The arithmetic of the animation

requestAnimationFrame, not setInterval

The browser calls your function once just before each screen repaint — about 60 times a second — and hands it a high-resolution timestamp. It syncs to the display and pauses automatically when the tab is hidden. setInterval(…, 16) can't promise either, so it drifts and tears. Always animate with requestAnimationFrame.

Delta-time: make speed independent of frame rate

The naïve mistake is advancing by a fixed amount per frame. Then a 144 Hz monitor runs your sun 2.4× faster than a 60 Hz one. The fix is to measure how many seconds actually elapsed and scale by that:

frame-rate-independent time 
const dt = (now - last) / 1000     // real seconds since the previous frame
t = (t + dt / 12) % 1             // rate = 1/12 ⇒ a full day always takes 12 s, any monitor

const hour = 6 + 12 * t            // map the 0..1 dial back to a clock: 06:00 … 18:00

t is a single dial from 0 to 1. % 1 wraps it back to dawn after dusk. Pausing is simply not calling requestAnimationFrame; scrubbing the time bar is setting t directly. The static sun-hours map ignores t entirely — it's the whole day summed up at once.

Easing — the S-curve that softens edges

A linear fade looks mechanical because it starts and stops abruptly. Smoothstep, x²·(3 − 2x), maps 0→0 and 1→1 but with zero slope at both ends — an S-curve that eases in and out. The hero animation uses it to soften the shadow's leading edge so cells fade across the boundary instead of snapping from gold to blue.

smoothstep 
const smooth = (x) => { x = Math.max(0, Math.min(1, x)); return x*x*(3 - 2*x); }

A·4Geometry

The two geometry helpers

Is this cell in shadow? — point-in-polygon by ray casting

To ask "is this point inside this polygon," shoot an imaginary ray from the point straight out to infinity and count how many edges of the polygon it crosses. Odd number of crossings → inside; even → outside. (Think of stepping across a fence: each crossing flips you in/out.) The code walks every edge and, for each, checks two things: does the edge straddle the point's height, and is the crossing point to one side — flipping a boolean each time it's a yes.

point-in-polygon (the even–odd rule) 
          ___________
         /           \         ray →  ✕     ✕        (2 crossings = even = OUTSIDE)
        /    • ───────────────→ ✕              ✕      (point inside: 1 crossing = odd)
       /              \
      /________________\
pip() — annotated 
function pip(px, py, poly) {
  let inside = false;
  for (let i = 0, j = poly.length - 1; i < poly.length; j = i++) {
    const a = poly[i], b = poly[j];
    // does edge a→b straddle the ray's height, and is the crossing to the right of px?
    if (((a.y > py) !== (b.y > py)) &&
        (px < (b.x - a.x) * (py - a.y) / (b.y - a.y) + a.x)) inside = !inside;
  }
  return inside;
}

A wall's shadow — project, then take the convex hull

A vertical wall's shadow isn't just the footprint moved over; it's the footprint and the footprint shifted by the shadow offset, with the outline wrapped tightly around both. That tight outline is the convex hull — imagine a rubber band snapped around all the points. (Andrew's monotone-chain algorithm builds it by sorting the points left-to-right and sweeping a lower edge and an upper edge.) The shift itself is exactly the vector from A·1: length L = h / tan(α), pointing away from the sun.

shadowOf() — where the trig becomes geometry 
function shadowOf(occ, s) {
  const L = occ.h / Math.tan(s.alt);      // ← A·1: shadow length
  const off = { x: -L * s.dir.x, y: -L * s.dir.y };   // away from the sun
  const moved = occ.foot.map(p => ({ x: p.x + off.x, y: p.y + off.y }));
  return occ.kind === 'overhead'
    ? moved                          // a floating slab: just the translated footprint
    : hull(occ.foot.concat(moved));   // a wall: wrap the band around base + top
}
The whole engine, in one breath sun(t) gives an angle (A·2) → tan turns the angle into a shadow length (A·1) → that length shifts a polygon (A·4) → pip asks which cells fall inside it (A·4) → sum that over the day (phase 04) and you have the sun-hours map.
